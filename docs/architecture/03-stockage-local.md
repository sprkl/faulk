# Stockage local du projet et mémoire audio

> **Décisions du fondateur du 2026-10-14 intégrées** (§ 6). Ce document reprend l'étude du 2026-10-13 sur le stockage local. Il suit le format de projet de [Modèle de projet et format sur disque](02-modele-projet.md) (dossier regroupé par piste, audio dans `blobs/<sha256>`, caches dans `.faulk/`), qui remplace la disposition à un seul document proposée par l'étude. Décidé : le dossier réel est le stockage par défaut (Chrome, Edge), l'OPFS avec export en archive le repli ; l'isolation cross-origin est acceptée, donc le streaming passe par `SharedArrayBuffer` ; les pistes audio (import et lecture) sont dans le MVP, l'enregistrement audio le suit immédiatement : les paragraphes sur l'enregistrement décrivent ce qui vient juste après. Le statut reste `draft` tant que le document n'a pas été vérifié contre le code.

La question : l'application web peut-elle travailler sur un projet stocké localement, avec ses fichiers audio, sans que tout soit dans la mémoire du navigateur ?

## Réponse courte

**Oui, le projet peut vivre sur disque, et non, tout n'a pas besoin d'être en mémoire.**

1. **Où vit le projet.** Dans Chrome et Edge (bureau), le projet peut être un **vrai dossier choisi par l'utilisateur** (File System Access, `showDirectoryPicker`) : visible dans l'explorateur de fichiers, versionnable avec git, sauvegardable. Firefox et Safari n'offrent pas ce dossier ; ils offrent l'**OPFS**, un système de fichiers privé au site, invisible pour l'utilisateur, soumis au quota et à l'éviction. Le dossier réel est donc un avantage Chromium, avec l'OPFS en repli et l'export `.faulkpack` pour les autres.
2. **Ce qui est en mémoire.** Seul ce qui joue ou va jouer doit être en mémoire, plus de petits caches (débuts de fichiers, aperçus de forme d'onde). `decodeAudioData` décode tout un fichier et ne convient pas aux longs enregistrements ; on peut lire des morceaux du fichier dans un Worker et les pousser vers l'`AudioWorklet` (streaming). Un projet de quelques dizaines de pistes tient même entièrement décodé (environ 23 Mo par minute de stéréo 48 kHz en float32) : **on peut charger les clips courts en mémoire et streamer les longs**.

## 1. Les options de stockage et leurs limites

### 1.1 File System Access (dossier réel)

| Point | État (octobre 2026) |
| --- | --- |
| `showDirectoryPicker`, `showOpenFilePicker`, `showSaveFilePicker` | Chrome et Edge bureau depuis la v86 (complet depuis la v105), Opera. **Pas Firefox** (position négative de Mozilla), **pas Safari**, **pas Chrome Android**. |
| Lecture | `FileSystemFileHandle.getFile()` renvoie un `File` (un instantané) ; `file.slice(a, b).arrayBuffer()` lit une plage sans charger le reste. Accès aléatoire, asynchrone. |
| Écriture | `createWritable()` écrit dans un fichier d'échange (`.crswap` dans Chrome) et remplace la cible à `close()`. Option `mode: "exclusive"` pour un seul écrivain. Chrome lance un contrôle Safe Browsing à la fermeture (`AbortError` possible). |
| Accès synchrone (`createSyncAccessHandle`) | **Réservé à l'OPFS.** |
| Mémoriser le dossier | Le `FileSystemDirectoryHandle` se range dans IndexedDB. Au retour : `queryPermission()` puis `requestPermission()` (geste de l'utilisateur obligatoire). |
| Permissions persistantes (Chrome 122+) | Invite à trois choix, dont « Autoriser à chaque visite ». Sans ce choix, l'accès dure jusqu'à la fermeture du dernier onglet du site et peut être **révoqué si l'onglet reste longtemps en arrière-plan**. Une PWA installée garde l'accès par défaut. |
| Dossiers interdits | Chrome refuse les dossiers système et sensibles (racine du disque, dossier du système, parfois tout le dossier de téléchargements) : l'interface gère le refus et propose un sous-dossier. |
| Changements externes | `FileSystemObserver` : livré dans Chrome et Edge 133 (bureau), observation récursive possible, sur ce que l'utilisateur a autorisé. Pas Firefox, pas Safari ; pas encore standardisé. |
| Quota | Un dossier de l'utilisateur **n'est pas compté dans le quota** et n'est **jamais évincé**. |

### 1.2 OPFS (Origin Private File System)

- `navigator.storage.getDirectory()` : disponible partout (Baseline).
- `createSyncAccessHandle()` dans un **Worker dédié** : lecture et écriture synchrones à une position, verrou exclusif (le mode `readwrite-unsafe` permet plusieurs poignées). Firefox 111+, Safari 15.2+, Chrome 102+.
- `createWritable()` sur l'OPFS : Chrome 86+, Firefox 111+, Safari seulement depuis la 26.0.
- **Invisible pour l'utilisateur** (pas de git, pas de sauvegarde système), **compté dans le quota**, **évincé avec toutes les données du site**.
- Le stockage le plus rapide du navigateur.

### 1.3 IndexedDB

Utile pour les métadonnées et pour **ranger les poignées de dossier**. Mauvais candidat pour l'audio : stockage par objets entiers, plus lent que l'OPFS, même quota, même éviction.

### 1.4 Quotas, persistance, éviction

| Navigateur | Mode « best-effort » (défaut) | Mode persistant (`navigator.storage.persist()`) |
| --- | --- | --- |
| Chrome / Edge | jusqu'à 60 % du disque | identique ; le navigateur entier plafonne à 80 % |
| Firefox | le plus petit de 10 % du disque ou 10 Gio | jusqu'à 50 % du disque, plafond 8 Tio |
| Safari (navigateur) | environ 60 % du disque par origine | non précisé |
| Safari (WebView) | environ 15 % | — |

- Le quota porte sur la taille totale du disque, pas l'espace libre : gérer `QuotaExceededError` partout. `estimate()` donne une estimation, pas un compte.
- `persist()` : Firefox affiche une invite ; Chrome et Safari décident sans invite selon l'engagement de l'utilisateur.
- **Éviction** : sous pression disque, le navigateur supprime en bloc les origines « best-effort » les moins récemment utilisées. **Safari** supprime toute donnée créée par script après 7 jours d'utilisation sans interaction avec l'origine (sauf application ajoutée à l'écran d'accueil ou au Dock).

**Conséquence** : l'OPFS est un bon cache et un repli acceptable, **jamais l'unique copie d'un projet** sans `persist()` accordé et sans export.

## 2. Le projet dans un vrai dossier

Faisable dans Chrome et Edge bureau, la cible prioritaire de Faulk.

- **Ouverture** : `showDirectoryPicker({ id: "faulk-project", mode: "readwrite" })`, poignée rangée dans IndexedDB ; la liste des projets récents est une liste de poignées. Au démarrage, `queryPermission({ mode: "readwrite" })` ; si la réponse est `prompt`, un bouton « Rouvrir le projet » déclenche `requestPermission()`.
- **Format** : le dossier de projet décrit dans [Modèle de projet et format sur disque](02-modele-projet.md). Les textes sont petits et se prêtent à git ; l'audio est dans `blobs/` (Git LFS côté utilisateur).
- **Écriture** : fichier par fichier, seulement les fichiers sales, chacun de façon atomique (§ 5.5).
- **Changements externes** (git checkout, éditeur de texte, autre outil) :
  - Chrome/Edge 133+ : `FileSystemObserver` récursif ; on recharge les fichiers dont le contenu a changé (comparer une empreinte pour ignorer ses propres écritures) ; on invalide le cache d'un blob touché.
  - Repli : relecture de `lastModified` et de la taille au retour du focus (`visibilitychange`) et avant toute lecture.
  - Un `File` obtenu par `getFile()` est un instantané : si le fichier change, la lecture lève `NotReadableError` ; le lecteur reprend `getFile()` et revalide l'empreinte.
  - Modification externe + modifications non enregistrées : décision produit (garder l'une ou l'autre version) ; la commande « recharger le projet » passe par `crates/commands` comme toute action.
- **Firefox et Safari** : pas de dossier réel. OPFS + export/import `.faulkpack` (ou `<input webkitdirectory>` pour importer un dossier en lecture seule, qui marche dans Firefox, mal dans Safari), ou le helper qui accède au vrai disque.

## 3. Stratégie mémoire pour l'audio

### 3.1 Ordres de grandeur

| Format | Octets/s | Par minute | 3 min | 1 h |
| --- | --- | --- | --- | --- |
| Stéréo 44,1 kHz float32 | 352 800 | 21,2 Mo | 63,5 Mo | 1,27 Go |
| Stéréo 48 kHz float32 | 384 000 | 23,0 Mo | 69,1 Mo | 1,38 Go |
| Stéréo 96 kHz float32 | 768 000 | 46,1 Mo | 138 Mo | 2,76 Go |
| Mono 48 kHz float32 | 192 000 | 11,5 Mo | 34,6 Mo | 0,69 Go |
| WAV stéréo 48 kHz 24 bits (disque) | 288 000 | 17,3 Mo | 51,8 Mo | 1,04 Go |
| WAV stéréo 48 kHz 16 bits (disque) | 192 000 | 11,5 Mo | 34,6 Mo | 0,69 Go |
| FLAC stéréo (≈ 55–60 % du WAV) | — | ≈ 7–10 Mo | — | — |

24 pistes stéréo de 4 min à 48 kHz entièrement décodées ≈ **2,2 Go**. Une session de 16 pistes mono d'une heure ≈ **11 Go** : impossible en mémoire. La mémoire WASM 32 bits plafonne à 4 Gio par instance, et un onglet souffre bien avant.

### 3.2 `decodeAudioData` : pratique mais tout en mémoire

- Décode **le fichier entier** en `AudioBuffer` float32 et le **rééchantillonne à la fréquence du contexte** ; le fichier compressé et le résultat coexistent pendant le décodage.
- Ni décodage partiel ni flux : correct pour les clips courts (< 1 min), mauvais au-delà.
- L'`AudioBuffer` vit côté JavaScript ; le moteur WASM en a besoin d'une copie dans sa mémoire linéaire : double occupation si on n'y prend pas garde.

### 3.3 Le streaming disque

Principe : seuls les **tampons de lecture anticipée** (quelques secondes par piste) sont en mémoire ; un thread disque les remplit en avance de la tête de lecture ; le thread audio lit ces tampons sans jamais attendre le disque.

```
 Disque (dossier utilisateur ou OPFS)
        │  lectures par plages (File.slice / SyncAccessHandle.read)
        ▼
 Worker « disque » (dédié)
   • ouvre les blobs, décode si besoin (WAV : direct ; FLAC/MP3/Opus : WebCodecs AudioDecoder ou décodeur WASM)
   • rééchantillonne vers la fréquence du contexte si besoin
   • tient un cache de blocs (LRU) et une lecture anticipée par piste
        │  blocs PCM float32
        ▼
 Anneau(x) lock-free en SharedArrayBuffer  ──►  AudioWorklet (moteur WASM)
   (ou, sans isolation : MessagePort + ArrayBuffer transférés)
```

- **Lecture anticipée** : 2 à 4 s par voix active. 48 pistes stéréo × 4 s ≈ **74 Mo**, quelle que soit la durée du projet.
- **Pré-chargement des débuts** : garder les 1 à 2 premières secondes de chaque clip pour démarrer instantanément sur un saut ou un lancement ; le streaming prend le relais.
- **Taille des lectures** : blocs de 64 à 256 Kio, alignés.
- **Débit** : 48 pistes WAV 24 bits ≈ 14 Mo/s, trivial pour un SSD. Aucune mesure publique fiable du débit OPFS ou File System Access : **à mesurer dans un spike**.
- **Sauts et boucles** : à chaque saut, le Worker vide et re-remplit les tampons ; en attendant, la voix lit le pré-chargement ou se tait, sans jamais bloquer le thread audio. Les boucles courtes restent en mémoire.
- **Enregistrement** : le chemin inverse. Le worklet pousse le PCM capté dans un anneau ; le Worker l'écrit par morceaux. Dans un dossier utilisateur, le fichier d'échange de Chrome ne remplace la cible qu'à `close()` : un plantage pendant la prise perdrait tout. On écrit donc en OPFS pendant la prise, puis on range le blob dans le projet à la fin.

### 3.4 Transport entre le Worker et l'AudioWorklet

Le worklet ne peut pas lire le disque (pas d'API de stockage dans `AudioWorkletGlobalScope`, et pas d'entrée-sortie sur le chemin audio).

| Option | Pour | Contre |
| --- | --- | --- |
| **`SharedArrayBuffer` + anneau lock-free** | Zéro allocation et zéro message dans le thread audio : conforme aux règles temps réel de Faulk. Le moteur WASM peut lire directement dans une mémoire partagée. | Exige l'**isolation cross-origin**. |
| `MessagePort` + `ArrayBuffer` transférés | Aucun en-tête particulier. | Chaque message crée des objets JS dans le thread audio (le `onmessage` du worklet tourne sur le thread de rendu) : allocation et ramasse-miettes dans le chemin audio. Acceptable pour un prototype, pas comme cible. |

**Isolation cross-origin** : `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` (ou `credentialless`).

- `require-corp` : toute ressource tierce doit être servie en CORS ou porter `Cross-Origin-Resource-Policy`. Le plus simple : **auto-héberger polices et bibliothèques** (Vite les empaquette de toute façon).
- `credentialless` : Chrome, Edge et Firefox, **pas Safari**.
- `COOP: same-origin` casse la relation avec les fenêtres d'autres origines (fenêtres d'authentification OAuth) : à prévoir si Faulk ajoute un compte en ligne.
- **Document-Isolation-Policy** (Chrome 137+) isole un document sans COOP/COEP sur tout le site ; Chromium seulement.

La [contrainte](../constraints/01-contraintes.md) rappelle que `SharedArrayBuffer` exige cette isolation. **Décidé le 2026-10-14** : l'isolation cross-origin est acceptée (tâche AU-0 du [découpage du MVP](../specs/02-decoupage-mvp.md), en phase 0) ; le streaming audio passe par des anneaux en `SharedArrayBuffer` (tâche AU-3), et le canal des commandes et des notes vers le worklet vise la même mémoire partagée (contrat CT-3). La voie `MessagePort`, où chaque message crée ses objets sur le thread de rendu, n'est plus qu'un repli à mesurer si la mémoire partagée se révélait impossible entre un Worker et le worklet.

### 3.5 Formats compressés : WebCodecs `AudioDecoder`

- Chrome/Edge 94+, Firefox 130+, Safari 26+, dans un Worker dédié et en contexte sécurisé.
- FLAC, Opus, MP3, AAC, Vorbis, PCM pris en charge dans environ 97 % des sessions mesurées ; vérifier avec `AudioDecoder.isConfigSupported()`.
- WebCodecs ne démultiplexe pas : il faut extraire soi-même les trames (en-têtes FLAC, trames MP3, pages Ogg, boîtes MP4).
- Le saut précis coûte plus cher dans un format compressé (FLAC a des tables de saut ; MP3 à débit variable non). D'où l'idée : **streamer du PCM non compressé**.
- Alternative : décodeur Rust (`symphonia`) compilé en WASM dans le Worker, identique dans le helper, cohérent avec « un seul moteur, deux cibles ».

### 3.6 Aperçus de forme d'onde

- Calculés une fois à l'import (dans le Worker) : min/max par bloc de 256 échantillons, plus des niveaux réduits (×4, ×16…) pour le zoom.
- Environ **45 Ko par minute** (int8) : se charge entièrement en mémoire.
- Cache régénérable dans `.faulk/cache/` (ou l'OPFS), exclu de git.
- Réalisé par AU-2 : § 5.12.

## 4. Ce que change le mode Boost

Depuis BO-1 (#102), la page tient le projet dans les deux modes et l'écrit elle-même, en Web comme en Boost : fichiers texte, blobs et caches (décision du fondateur du 2026-11-06, confirmée par le lead pour AU-7 : « la page possède le projet »). Depuis AU-7 (#116), le helper lit les fichiers audio du dossier que la page a ouvert, et seulement ceux-là (§ 5.13). Il annonce `disk: true` dans `hello` (`crates/helper/src/server.rs`). Ce qui suit décrit le code tel qu'il est.

- **Le son ne traverse pas le lien.** Le helper ne reçoit que les octets du moteur (`ControlMsg`) et les messages de la session. Ni les blobs, ni les caches PCM, ni les échantillons importés ne passent par le WebSocket. Mesures : un import d'une heure en Boost envoie 32 octets au helper (§ 5.9) ; la lecture native des clips ne fait passer aucun octet du blob dans une trame, dans un sens comme dans l'autre (test `crates/helper/tests/folder.rs`, § 5.13).
- **L'import (AU-1) tourne dans la page, dans les deux modes.** Le pipeline est dans le Worker du magasin de projet (`web/src/lib/audio/import/`, `web/src/lib/storage/worker.ts`). Il écrit `blobs/` et `.faulk/cache/pcm/` dans le dossier que la page tient. L'import natif (un chemin donné par un agent) est une tâche à part, #778.
- **Les lectures disque (AU-3) tournent là où joue le moteur.** En Web, elles se font dans le Worker de préparation de la page (`web/src/lib/audio/stream/executor.ts`). En Boost, le moteur Web est suspendu et c'est le fil disque du helper (`crates/helper/src/disk.rs`, `spawn_disk`) qui sert le planificateur de son moteur, depuis le dossier du projet, avec les mêmes règles (§ 5.13).
- **Les écritures.** La page écrit le dossier dans les deux modes. Le helper n'écrit aucun fichier du projet. Il a une écriture confinée au dossier (`ProjectFolder::begin`, atomique par `.faulk/tmp/`), qui refuse les fichiers du projet et les données du dossier : l'export audio en Boost s'en sert pour écrire `exports/<nom>.wav` (#319, § 5.13). Le seul fichier que le helper écrit hors d'un dossier de projet est sa propre configuration, la liste des dossiers que l'utilisateur lui a montrés (`folders.json`, dans son dossier de configuration, à côté de son jeton).
- **Les projets du navigateur (OPFS).** Un projet OPFS reste invisible au helper : en Boost, ses clips audio restent muets, et le panneau Clips le dit (« Enregistrer sous » dans un dossier, SV-3). L'ouverture d'un `.faulkpack` par le helper, prévue avant BO-1, est une tâche à part, #779.

## 5. Proposition pour le MVP

### 5.1 Emplacement

| Navigateur | Stockage du projet |
| --- | --- |
| Chrome / Edge bureau | **Dossier réel** choisi par l'utilisateur (défaut, décision du 2026-10-14), poignée en IndexedDB, permission « à chaque visite » encouragée. Caches en OPFS ou dans `.faulk/cache/`. Tâche SV-2. |
| Firefox / Safari, ou dossier refusé | **OPFS** + `navigator.storage.persist()` + export/import `.faulkpack` (archive zip du dossier). Avertissement clair : « vos projets sont dans le navigateur ; exportez-les ». Tâche SV-3. |
| Mode Boost (tous navigateurs) | Le dossier réel que la page a ouvert, et que la page écrit. Le helper n'y lit que les blobs et les caches PCM, pour sa lecture native, une fois que l'utilisateur le lui a montré (AU-7, § 4 et § 5.13). |

Une **seule abstraction de stockage** dans le Worker disque (`ProjectStore` : lister, lire une plage, écrire atomiquement, observer), avec trois implémentations : dossier File System Access, OPFS, helper. Le format du dossier est identique dans les trois cas : un projet OPFS exporté est un dossier de projet ordinaire.

### 5.2 Ce qui va dans `.faulk/`

Le dossier `.faulk/` (ignoré par git) complète l'arborescence du [modèle de projet](02-modele-projet.md) :

```
.faulk/
  cache/       # binary snapshot of the whole project, waveform peaks, decoded PCM: regenerable
  tmp/         # temp files for atomic writes, takes being recorded
  session.json # session state: solo, arming and monitoring per track, chosen MIDI input (restored on reopen, never versioned)
  view.json    # view state (zoom, scroll, selection)
  lock         # open lock (session, timestamp)
```

### 5.3 Format des fichiers audio

Les études divergent ; la proposition à trancher :

- **Le blob garde les octets d'origine** de l'import, pour que l'empreinte corresponde au fichier de l'utilisateur et que la déduplication fonctionne ([modèle de projet](02-modele-projet.md) § 3).
- **Fichiers compressés (MP3, AAC, Opus, Ogg, FLAC)** : pour streamer sans coût de décodage dans le chemin de lecture, deux options. (a) Décoder une fois à l'import vers un PCM rangé comme *second blob* référencé par le clip (double espace, mais versionné et identique sur toutes les machines). (b) Décoder vers un PCM dans `.faulk/cache/`, régénérable (pas de double espace dans git, mais un coût au premier chargement sur une nouvelle machine). **Décision à prendre.**
- **Rééchantillonnage** : **à la lecture** (tâche AU-4 du [découpage du MVP](../specs/02-decoupage-mvp.md)), dans le lecteur de clips du moteur, vers la fréquence du moteur (contexte audio en Web, périphérique en Boost, qui peut changer en cours de session) ; jamais à l'import, parce qu'une fréquence de projet fixe ne supprimerait pas ce besoin.

### 5.4 En mémoire et streamé

| En mémoire | Streamé depuis le disque |
| --- | --- |
| Le modèle du projet (structures Rust compactes), la pile d'annulation | Les clips longs (seuil proposé : > 30 s ou > 10 Mo décodés) |
| Les clips courts et échantillons (< 30 s), décodés une fois | Les enregistrements en cours (écriture) |
| Les 1 à 2 premières secondes de chaque clip long | |
| Les tampons de lecture anticipée (2 à 4 s par voix active) | |
| Les aperçus de forme d'onde (≈ 45 Ko/min) | |
| Les modules (WASM compilé) | |

Budget visé (24 pistes, 5 min) : moins de 300 Mo de mémoire audio, quelle que soit la durée totale des fichiers.

Le seuil par clip ne suffit pas à tenir ce budget : beaucoup de clips courts peuvent le dépasser à eux seuls. Le PCM décodé a donc un **budget global** (proposition : 300 Mo, réglable), tenu par le Worker disque :

- les clips courts, les débuts préchargés et les tampons de lecture anticipée puisent dans ce même budget ;
- au-delà, le Worker **évince** en priorité le PCM des clips qui ne jouent pas et ne sont pas proches de la tête de lecture (LRU), puis le préchargement des clips inactifs ; un clip évincé repasse en streaming ou est redécodé à la demande ;
- les tampons des voix en lecture ne sont jamais évincés ; si eux seuls dépassent le budget, l'interface l'affiche plutôt que de couper le son ;
- le compteur d'occupation est visible dans l'état du moteur (`Feedback.pcm_kib`, AU-3) ; sa mesure revient à AU-3 (§ 5.11), QA-7 n'ayant pas pu la faire avant que le compteur existe.

**Étape intermédiaire acceptable** : livrer d'abord « tout décodé en mémoire » avec une limite affichée (par exemple 1 Go de PCM par projet), puis le streaming. L'architecture (Worker disque + anneau vers le worklet) doit cependant être posée dès le départ, sinon la bascule touchera le moteur.

### 5.5 Écritures atomiques

- **Fichiers texte du projet** : seuls les fichiers sales sont écrits, après un court délai de regroupement (environ 1 s après la dernière commande, puisque toute action est une commande). Chacun est écrit dans `.faulk/tmp/` via `createWritable()` + `close()`, puis déplacé vers sa place par `move()` (disponible dans Chrome pour les fichiers locaux et dans l'OPFS ; **à valider dans le spike**, sinon écriture directe par `createWritable`, qui remplace déjà la cible à la fermeture).
- **Cohérence entre fichiers** : un enregistrement touche parfois plusieurs fichiers. L'instantané de cache n'est réécrit qu'après tous les fichiers ; à l'ouverture, la relecture des fichiers modifiés depuis l'instantané rattrape un enregistrement interrompu.
- `createWritable` ne modifie la cible qu'à `close()` : un onglet fermé pendant l'écriture laisse l'ancien fichier intact (le `.crswap` peut rester : nettoyé au démarrage suivant).
- **Enregistrement audio** : par morceaux dans l'OPFS (poignée synchrone, `flush()` toutes les quelques secondes, en-tête WAV corrigé à la fin), puis rangement dans `blobs/` à la fin de la prise. Au redémarrage, une prise orpheline est proposée en récupération.
- `beforeunload` : prévenir si une écriture est en cours, sans compter dessus.

### 5.6 Modes de défaillance

| Défaillance | Détection | Réponse |
| --- | --- | --- |
| Permission perdue (nouvelle session, onglet longtemps en arrière-plan, révocation) | `queryPermission()` ≠ `granted`, ou `NotAllowedError` | Pause du transport sur les pistes concernées, bandeau « Rétablir l'accès au dossier » (geste → `requestPermission()`) ; les modifications restent en mémoire et dans un journal OPFS en attendant. |
| Dossier déplacé ou renommé | `NotFoundError` sur la poignée | Proposer de rouvrir le dossier ; vérifier l'identifiant de projet dans `project.json`. |
| Blob absent ou modifié hors de Faulk | `NotFoundError`, `NotReadableError`, empreinte différente, `FileSystemObserver` | Clip « hors ligne » (silence, jamais de plantage), recherche par empreinte, ou demande à l'utilisateur. |
| Modification externe des fichiers texte (git checkout) | `FileSystemObserver` ou comparaison au retour du focus | Recharger si pas de modification locale ; sinon demander. |
| Quota dépassé (OPFS) | `QuotaExceededError` | Arrêter proprement l'écriture, garder la partie écrite, avertir avec `estimate()`, proposer l'export ou le nettoyage des caches. |
| Disque plein (dossier réel) | Erreur d'écriture | Même réponse ; l'enregistrement s'arrête sans corrompre la prise. |
| Éviction de l'OPFS (Firefox/Safari ; Safari 7 jours) | Projet absent au démarrage | Prévenir en amont : `persist()`, rappel d'export, « dernier export » affiché. Les caches évincés se régénèrent. |
| Onglet fermé pendant une écriture | Fichier d'échange orphelin, `.faulk/tmp/` non vide | Ancien fichier intact ; nettoyage au démarrage ; récupération des prises orphelines. |
| Deux onglets sur le même projet | Verrou `.faulk/lock` + Web Locks API ou `BroadcastChannel` | Deuxième onglet en lecture seule. |
| Lecture disque trop lente (sous-alimentation de l'anneau) | Compteur côté worklet | Silence sur la voix concernée, jamais d'attente ; compteur affiché ; lecture anticipée augmentée. |

### 5.7 Limites acceptées pour le MVP

- Dossier réel : Chrome et Edge bureau uniquement. Firefox et Safari : OPFS + export, sans dossier visible, sans git, sans surveillance des changements.
- Pas de mobile.
- Formats d'import : WAV et AIFF directs ; compressés selon la décision du § 5.3 ; la liste décidée par AU-1 est au § 5.9 (Opus depuis #609).
- Pas d'écriture concurrente page + helper : une seule autorité d'écriture.

### 5.8 Brouillons et projets du navigateur (SV-3, #96)

Ce qui est écrit dans `web/src/lib/storage/` (`opfs.ts`, `storage.svelte.ts`) et `crates/project-wasm/src/pack.rs`. Le code fait foi.

- **Où** : `faulk/browser/<uuid>/` dans l'OPFS du site, un répertoire par projet, au format de dossier ordinaire (le nom du répertoire n'est pas l'identité du projet : elle est dans `project.json`). Un répertoire de l'OPFS est un `FileSystemDirectoryHandle` : le même `ProjectStore` (Worker, mêmes écritures atomiques) l'écrit, il n'y a pas de seconde implémentation. Sans `createWritable` (Safari avant 26) l'OPFS n'est pas utilisé et le projet reste dans l'onglet, avec l'avertissement avant de partir.
- **Brouillon** : tant qu'aucun dossier n'est choisi, un projet dont le *projet* a changé (pas seulement la sélection ou un solo : le cœur distingue `project_dirty`) est écrit dans l'OPFS comme il le serait dans un dossier (1,5 s après la dernière modification). À la réouverture de la page, le plus récent des brouillons non ouverts ailleurs se rouvre de lui-même (#474 : le stockage du navigateur ne demande aucune permission, donc aucun bandeau ni clic), sauf si le dernier dossier ouvert est plus récent ; seul un dossier dont le navigateur réclame la permission garde un bandeau, avec un seul bouton principal « Rouvrir « nom » ». « Enregistrer sous » demande d’abord le nom du projet (champ prérempli, #627), puis le dossier : le projet est écrit dans un sous-dossier de ce nom (nettoyé pour le système de fichiers) créé dans le dossier choisi, ou déjà là et vide, un sous-dossier qui contient des fichiers est refusé, et le projet prend ce nom par `project.rename` ; vers un dossier vide, il reprend le même projet (même identité, blobs copiés, verrou de l'identité repris) et supprime le brouillon une fois le dossier complet et retenu parmi les projets récents, avant que la page affiche « enregistré » (un rechargement après « enregistré » ne trouve donc pas le projet en double ; un rechargement pendant la suppression elle-même le peut encore, car supprimer avant de retenir le dossier risquerait de ne plus rien proposer ; si le dossier n'est pas confirmé parmi les récents, ou si la suppression échoue, le brouillon reste) ; « Enregistrer » et le dossier proposé à l'export attendent la fin du déplacement (copie, écriture, rattachement) ; un échec laisse le brouillon et ses verrous. Un brouillon n'est supprimé que par « Enregistrer sous » ou par un clic de l'utilisateur, après confirmation ; « Nouveau » ou « Ouvrir » le gardent (le menu les liste).
- **Sans dossier à choisir** (Firefox, Safari) : l'OPFS est le stockage normal. Le dernier projet rouvre seul ; « Enregistrer » le garde dans le navigateur ; `navigator.storage.persist()` est demandé à la première écriture ; l'avertissement « tes projets sont dans le navigateur ; exporte-les » est un bandeau (plus net si `persist()` a été refusé) et dans le menu.
- **Verrous (Web Locks)** : un par identité de projet (un seul onglet écrit un projet) et un par répertoire (`dir.<uuid>`), pris *avant* de créer le répertoire et tenus tant que l'onglet l'utilise. Au démarrage, un répertoire sans `project.json` dont personne ne tient le verrou (un onglet fermé en pleine première écriture ou en plein import) est supprimé ; un répertoire en cours de création dans un autre onglet est laissé.
- **Quota plein** (`QuotaExceededError`) : bandeau propre (exporter ou libérer de la place, réessayer), modifications gardées dans l'onglet, nouvel essai toutes les 10 s. Chaque fichier est remplacé en entier ou pas du tout ; un enregistrement interrompu entre deux fichiers laisse un dossier qui s'ouvre, car le fichier d'un clip n'est écrit qu'après ses notes (tests : un enregistrement qui ajoute, puis un qui renomme et supprime une piste, coupés à chaque fichier). Ce dossier peut mêler deux versions du projet (les pistes et clips sont trouvés en listant les répertoires, `project.json` vient en dernier, les suppressions après) : l'onglet, tant qu'il est ouvert, garde la version complète en mémoire et réessaie.
- **`.faulkpack`** : l'export reprend le projet tel qu'il est (modifications non écrites comprises) et les blobs du stockage, est écrit en flux, fichier par fichier, par `PackWriter` (déterministe, #617) : les fichiers du projet entrent dans le cœur, chaque blob est lu dans le magasin par morceaux de 1 Mio et la zip sort au fur et à mesure, vers un fichier que l'utilisateur choisit (`showSaveFilePicker`, dès 64 Mio de médias, la boîte s'ouvre avant toute attente) ou vers un téléchargement (là où le navigateur n'a pas cette boîte : il garde alors la zip dans un Blob, sur disque quand elle est grosse, et la page vérifie qu'il y a de la place) ; la mémoire de la page ne dépend donc pas de la taille du projet, avec progression et annulation (`project.cancel_export_pack`) : le bandeau d'export est là dès le clic, boîte de dialogue et préparation comprises (l'annulation y compte déjà), et ne disparaît qu'une fois le dernier morceau écrit et le fichier fermé ; une annulation pendant l'attente de la file l'arrête aussitôt, et tant qu'il n'écrit pas encore (boîte de dialogue, file tenue par un import), le bandeau d'un import ou d'un téléchargement en cours passe devant le sien, avec son bouton Annuler ; un export qui écrit garde le sien devant (#737) ; l'import se fait lui aussi en flux (#682), par la règle stricte de tous les hôtes (`project::file::PackReader`, sur laquelle `import_pack` repose : seuls les chemins du format, fichiers stockés ou déflatés seulement, longueurs comptées à la production, CRC de chaque fichier, empreinte de chaque blob, nom de l'en-tête local égal à celui du répertoire). Là où le navigateur garde des projets, le Worker du magasin lit le pack par les plages que le cœur demande (`pw_unpack_*`, sa propre instance du module) et écrit chaque blob dans un nouveau répertoire au fil de l'eau ; un premier passage ne lit que les fichiers propres du projet, pour en connaître l'identité avant tout média ; les fichiers du projet reviennent à la page, qui vérifie l'identité, les écrit (`project.json` en dernier) et ouvre le projet comme un projet du navigateur : un projet de même identité déjà ouvert ou gardé dans le navigateur n'est jamais remplacé, et le répertoire fait pour l'import est supprimé. Progression et annulation (`project.cancel_import_pack`, qui arrête aussi un téléchargement et un import en attente, et rend `cancelled` et `too_late` : le nombre d'imports arrêtés et de ceux dont le projet s'ouvrait déjà ; si aucun n'a pu être arrêté et que l'un était trop tard, l'appel est refusé ; là où le navigateur ne garde pas de projets, la lecture entière du pack se lit par morceaux, le bandeau d'import montre le même bouton Annuler et un clic arrête la lecture, #735) ; un échec, une annulation ou un manque de place suppriment le répertoire. Limites : celles du format (2 Gio par blob, 16 Gio au total) ; la session garde jusqu'à la fin les fichiers propres du projet (128 Mio au plus) et les blobs d'automation dense (`FKAUTO01`, que l'ouverture lit), 512 Mio en tout (la trame de dossier que la page prépare à l'ouverture), jamais un autre blob ; avant d'écrire les médias, la page compare la place libre du navigateur à la taille que le répertoire du pack déclare pour ses blobs ; le bandeau du téléchargement donne son avancement quand l'hôte annonce la longueur ; mesuré en natif sous un allocateur qui compte (`pack_import_stream.rs`, blob de 600 Mio, un petit projet) : 14 Mio au plus ; dans Chromium (`pack-import.spec.ts`, audio de bruit), 300 et 500 Mio s'importent en 5,1 et 7,1 s, la mémoire de la page (tas JS et tampons) monte de 5,7 et 1,4 Mio, l'instance du module dans le Worker tient 5,7 Mio, aucune Long Task, écart maximal d'un minuteur de 5 ms 14 ms ; avant, un pack de 180 Mio faisait monter la page de 536 Mio et la bloquait 5,8 s d'un seul tenant (après : +5,3 Mio, aucune Long Task). Là où le navigateur ne garde rien (le projet vit dans l'onglet), le pack est lu en entier, 192 Mio au plus (`MAX_PACK_BYTES`, `pw_pack_import`). La zip est déflatée dans le Worker du magasin quand le projet y est lu (#685) : le Worker a sa propre instance du module du cœur pour la session `pw_pack_*`, lit les blobs lui-même et envoie chaque morceau de zip à la page, qui l'écrit là où l'utilisateur l'a choisi et donne son accord avant le morceau suivant ; le fil principal ne déflate plus (hors Worker, par exemple dans un test, le cœur de la page la fait comme avant).
- **Commandes des actions de stockage (#323)** : chaque bouton du bandeau et du menu envoie une commande, il n'a plus de chemin privé. `project.list_stored` (requête : la page relit ses listes, les met dans le contexte du cœur, `Context::stored`, et la commande répond avec les dossiers récents `{ id, name }` et les projets du navigateur `{ dir, name }`), `project.reopen_last` (bandeau « Rouvrir »), `project.open_folder`, `project.open_recent { id }`, `project.open_browser_project { dir }`, `project.delete_browser_project { dir }`, `project.keep_mine` et `project.load_folder_version` (conflit de SV-2), `project.allow_access` (« Autoriser »). Toutes sont `live`, non annulables ; le contrat réserve `x-destructive` aux éditions (`Meta::check`), donc **aucune n'est marquée destructive** : c'est la page qui demande, **quel que soit l'appelant** (supprimer un projet du navigateur, remplacer les fichiers du dossier par le projet, remplacer le projet par le dossier ; ouvrir un autre projet demande déjà quand des modifications seraient perdues). Depuis AG-4 (#100), l'appel d'un agent à l'une d'elles (et à `project.new`, et aux ouvertures `open_recent`, `open_browser_project`, `reopen_last`, `open_url`) attend d'abord la réponse de l'utilisateur à la question de l'agent (`web/src/lib/agents/guard.ts`, `STORAGE_GUARDED`) ; une fois autorisée, le stockage ne repose pas sa propre question (`allowed`), et l'agent reçoit la réponse une fois l'action faite, ou un refus typé (`confirmation.declined`, `confirmation.timeout`, `not_done`). Un clic de l'utilisateur garde le comportement d'avant : la réponse à la commande dit seulement qu'elle est acceptée. Gardes de `ProjectStorage` : un nom (`dir`, `id`) qui n'est pas dans la liste que la page tient est refusé par un avis, jamais passé tel quel à l'OPFS ; `keep_mine` et `load_folder_version` ne font rien (avis) hors conflit, et revérifient le conflit après la réponse ; le sélecteur de dossier et l'invite d'autorisation ne s'ouvrent que depuis un clic (`navigator.userActivation`), sinon un avis le dit ; l'invite n'est demandée que si l'autorisation est perdue. Une question ouverte garde la file du stockage : les écritures du projet attendent la réponse (rien n'est perdu, elles partent après).
- **Ouvrir un `.faulkpack` par son lien (#497)** : `project.open_url { url }` (commande « live », sans annulation : ouvrir n'est pas une édition ; on revient au projet d'avant par la liste des projets). Le cœur vérifie la forme du lien (`https`, ou `http` vers `localhost`, `127.0.0.1` ou `[::1]` seulement, sans identifiants, 2 048 caractères au plus) ; la page le relit avec `new URL` et refuse aussi `http` quand elle n'est pas elle-même servie depuis cet ordinateur (`web/src/lib/storage/open-url.ts`). Le téléchargement se fait sans cookies ni identifiants (`credentials: 'omit'`, `referrerPolicy: 'no-referrer'`), en CORS, hors de la file du stockage et un à la fois ; la taille est refusée avant lecture sur `Content-Length` puis pendant la lecture (le flux est annulé dès la limite dépassée : celle du format là où le navigateur garde des projets, le téléchargement étant alors écrit au fil de l'eau dans `.faulk/tmp/download.faulkpack` du nouveau répertoire puis lu de là, `MAX_PACK_BYTES` sinon) ; le bandeau du téléchargement offre « Annuler » (`project.cancel_import_pack`) ; une redirection vers un lien que la page ne prendrait pas, un hôte muet 30 s, une erreur réseau, CORS ou HTTP donnent « Impossible de télécharger ce projet depuis <hôte>. » avec « Importer un fichier… ». Le pack suit ensuite le chemin d'un import de fichier (là où le navigateur garde des projets, lu en flux par `PackReader` dans le Worker depuis le fichier téléchargé, sinon `pw_pack_import` en entier ; nouveau répertoire, ouverture), sauf qu'un pack dont le navigateur garde déjà le projet rouvre cette copie au lieu d'être refusé. Le lien `/app?open=<url>` est lu au montage du shell et retiré aussitôt de l'adresse ; la page demande toujours avant de télécharger, dans une boîte qui nomme l'hôte et montre le lien entier, puis envoie la commande. Aucun contenu du pack n'est exécuté.
- **Pas vérifié sous Firefox et Safari** (aucun moteur de ces navigateurs dans les tests) : `move()` sur l'OPFS, la forme de `QuotaExceededError`, l'invite de `persist()`.

### 5.9 Import d'un fichier audio (AU-1, #110)

Ce qui est écrit dans `crates/audio-import`, `crates/audio-import-wasm` et `web/src/lib/audio/import/`. Le code fait foi.

- **Où.** Le pipeline est écrit une fois en Rust (`crates/audio-import` : SHA-256 en flux, décodage par `symphonia` 0.6 sans aucune fonction SIMD, pour que les deux cibles exécutent le même code scalaire, métadonnées, disposition des fichiers lus directement, en-tête du cache PCM). Dans la page, il tourne dans le Worker du magasin de projet (`storage/worker.ts`), le seul endroit qui écrit le dossier : un module WebAssembly à part (`audio-import-wasm`, ABI C `ai_*`, 1,75 Mo depuis #609 (1,36 Mo avant ; 465 Ko en brotli), chargé au premier import seulement), qui lit le fichier par plages par une seule importation synchrone (`env.ai_read`, servie par `FileReaderSync`) et décode paquet par paquet, de sorte que le Worker reprend la main entre deux étapes (écritures asynchrones, autres appels, annulation). Le Worker envoie sa progression (`{ id, progress }`), et chaque message de progression repousse le délai de 10 minutes du magasin : un import d'une heure n'est pas pris pour un Worker muet. Sans Worker (le magasin dans la page), l'import est refusé (`unavailable`).
- **Étapes.** (1) Hacher le fichier en le copiant dans `.faulk/tmp/import-<id>` ; (2) le décoder entièrement (un fichier abîmé est refusé à l'import, pas à la lecture), en écrivant le cache PCM dans un autre fichier temporaire s'il n'est pas lu directement ; (3) seulement alors, déplacer la copie dans `blobs/<sha256>` (ou la jeter si le dossier a déjà ce blob : un seul blob par fichier, quel que soit le nombre d'imports) et le cache dans `.faulk/cache/pcm/`. Un échec à n'importe quelle étape supprime les fichiers temporaires et ne range rien. Là où `move` est refusé, le fichier est écrit en place par `createWritable` (atomique à la fermeture) et supprimé si l'écriture échoue : un blob à moitié écrit ne reste jamais sous son empreinte. Deux imports du même fichier dans un onglet se suivent pour le rangement ; le nettoyage d'un rattachement (`cleanUp`) laisse les fichiers temporaires d'un import en cours (verrou Web Lock `faulk.import.<id>`). Le contrôleur range l'import dans sa file : un enregistrement, un « Enregistrer sous » ou une ouverture n'a jamais lieu au milieu d'un import (l'autosauvegarde attend la fin) ; il ajoute l'estampille du blob à celles de ses propres écritures, si bien que la surveillance du dossier ne prend pas l'import pour une modification extérieure. Un projet sans place reçoit d'abord son brouillon dans l'OPFS.
- **Formats** (décidé par AU-1) : WAV (PCM 8 à 32 bits, flottant 32 et 64, A-law, µ-law, ADPCM IMA et Microsoft), AIFF et AIFF-C, CAF, FLAC, MP3 (et MP1, MP2), AAC-LC en MP4, M4A ou ADTS, ALAC, Ogg Vorbis : WAV et tout ce que `decodeAudioData` de Chromium décode. **Opus** (#609), en Ogg et en WebM/Matroska, mono ou stéréo (famille de correspondance des canaux 0, ou famille 1 d'un seul flux dans l'ordre) : `symphonia` 0.6 démultiplexe (Ogg et Matroska) mais n'a pas de décodeur Opus ; les paquets vont à `opuscule` (Rust pur, MPL-2.0 comme `symphonia`, conforme aux 12 vecteurs de la RFC 8251 en mono et en stéréo), compilé en flottant sans `std` : toutes ses fonctions mathématiques passent par le crate `libm` en Rust, si bien que la page et le helper décodent un Opus au bit près. Un Opus d'une autre disposition de canaux (surround, ambisonie : familles 2, 3, 255, ou famille 1 de plus de deux canaux) est refusé par son nom (`unsupported_codec`), comme un Matroska qui contient un autre codec que l'Opus (avant #609, tout Matroska était `unsupported_format`). Les retards d'encodeur sont retirés partout : étiquette LAME du MP3, positions des pages Ogg, liste d'éditions MP4 de l'AAC (lue par Faulk, `symphonia` ne l'applique pas ; la longueur gardée y est donnée dans l'échelle de temps du film, souvent 1 000 par seconde, donc à une demi-milliseconde près), pré-saut (*pre-skip*) de l'en-tête `OpusHead` dans les deux conteneurs, et `DiscardPadding` du dernier bloc d'un WebM (lu par Faulk en parcourant les en-têtes des éléments du fichier, `webm.rs` : `symphonia` le lit mais l'ignore ; un enregistrement de navigateur n'en écrit pas, il s'arrête sur un paquet entier) ; les frames d'un fichier sont donc celles de sa musique, sans amorce ni remplissage. Limites : celles du modèle (8 à 768 kHz, 1 à 64 canaux, moins de 2^40 frames) ; aucune taille maximale propre au pipeline, qui travaille en flux (le disque ou le quota décident).
- **Lu directement ou mis en cache** (décision 3 du § 6, proposition par défaut retenue, présentée au fondateur par la PR) : un WAV ou un AIFF d'échantillons entiers de 16, 24 ou 32 bits ou flottants de 32 bits n'a **pas de cache** : AU-3 lira ses échantillons dans le blob, par plages, avec sa disposition (`PcmLayout` : position des données, codage, canaux, frames ; la conversion en `f32` est celle de `symphonia`, testée échantillon par échantillon). Tout autre fichier a un **cache PCM** `.faulk/cache/pcm/<sha256>.pcm` : en-tête de 32 octets (`FKPCM001`, fréquence, canaux, frames, version du décodeur), puis les frames en `f32` entrelacés, petit-boutiste. Il est nommé par le blob (partagé par tous les clips du même fichier), jamais versionné, valide seulement si son en-tête et sa taille sont exactement ceux du média et de la version du décodeur ; sinon il est refait. Coût : un décodage par machine (un MP3 de 3 minutes, environ 64 Mo de cache en stéréo 44,1 kHz) contre un second blob versionné qu'il faudrait copier partout.
- **Le cache absent se régénère à l'ouverture**, là où est le disque : dans la page, dans les deux modes. Après chaque rattachement d'un projet (ouverture, réouverture d'un brouillon, import d'un `.faulkpack`, « Enregistrer sous », qui copie `blobs/` mais pas `.faulk/`), le contrôleur demande en arrière-plan au Worker les caches qui manquent pour les médias des clips du projet (`ensureAudioCache`) ; un blob absent est compté (le clip sera « média absent », AU-5), un blob qui ne se décode plus comme le projet le dit est signalé et n'a pas de cache.
- **Commandes.** `clip.choose_audio { track }` (live) ouvre la fenêtre de fichiers de la page, seulement sur un clic (sinon un avis) ; `clip.cancel_audio_import` (live) arrête l'import en cours (le fichier en cours n'est pas gardé, les suivants ne sont pas importés) ; chaque fichier choisi passe par le pipeline, ses métadonnées sont mises dans le contexte du cœur (`pw_stage_media`, `Context::media`), puis `clip.import_audio { track, media }` (édition annulable) crée le clip dans la réserve de la piste audio : le fichier entier, 0 dB, sans boucle, nommé d'après le fichier. L'annulation est `clip.delete`, désormais valable pour un clip audio, dont l'inverse est `clip.restore_audio` ; le blob reste (nettoyage sur demande seulement). Un agent peut faire un clip d'un fichier que le projet utilise déjà, par son empreinte. Depuis AU-5 (#114), l'import peut aussi poser le clip dans une case ou dans l'arrangement, et un clip dont le blob manquait à l'ouverture est marqué « média absent » (`media_missing` de `clip.get`), jusqu'à ce que la page remette le fichier.
- **Un fichier par lien, pour un agent (#664).** Décision du fondateur (2026-11-06) : l'agent donne une URL, la page demande la confirmation de l'utilisateur, puis télécharge et importe le fichier. `clip.import_audio_url { track, url }` (live, sans annulation propre) : le cœur vérifie la piste (audio) et la forme du lien avec le contrôle de `project.open_url` (`https`, `http` seulement vers `localhost`, `127.0.0.1` ou `[::1]`, ni nom d'utilisateur ni mot de passe, 2 048 caractères au plus) ; la page le relit avec l'analyseur du navigateur et son propre hôte (`http` local seulement depuis une page servie par cet ordinateur, sinon `url.refused`). Puis la question d'AG-4 (`importAudio` : hôte du lien, nom du fichier tiré du dernier segment du chemin, nom de la piste ; 45 s ; le titre ne montre que l'hôte, le nom choisi par l'agent est dans le texte, sans guillemets, caractères de contrôle ni marques de sens d'écriture, 80 caractères au plus) : **rien n'est envoyé à l'hôte avant « Autoriser »**, si bien que la taille n'est connue qu'au début du téléchargement (affichée dans le panneau des clips). Autorisé, le fichier est téléchargé tout de suite, hors de la file des imports (`streamPack` : sans cookies, identifiants ni référent, en CORS, une redirection vérifiée comme le lien, la longueur annoncée refusée au-delà de `MAX_AUDIO_URL_BYTES`, 192 Mio, et les octets comptés et coupés au-delà, abandon après 30 s sans données), gardé en mémoire puis passé au même import qu'un fichier choisi, dans la même file : son contenu est décodé et vérifié par le pipeline quelles que soient son extension et son type (le type annoncé par l'hôte n'est pas gardé) ; le clip est fait par `clip.import_audio` au nom de l'agent, une entrée d'historique que l'utilisateur annule. Réponse à l'agent : `{ clip, media }`, ou un refus typé, rien de changé : `confirmation.declined`, `confirmation.timeout`, `url.refused`, `import.busy` (le même lien est déjà en cours : un agent qui rappelle après `page.timeout`), `download.too_big`, `download.unreachable` (réseau, CORS, réponse en erreur, redirection, silence), `import.cancelled` (`clip.cancel_audio_import`, qui arrête aussi les téléchargements, ou l'appel retiré), `import.project_changed` (un autre projet ouvert avant le tour du fichier : rien n'y entre) et `import.<raison>` du pipeline (`import.unsupported_format`…). Le même appel refait (même lien, même piste, dans les 10 minutes, le clip encore là) répond le clip déjà fait, sans question ni téléchargement : c'est le rappel d'un agent qui a reçu `page.timeout`. La taille décodée n'est pas bornée au-delà des limites du modèle, comme pour un fichier choisi (#780). Le téléchargement et l'import n'existent que derrière la réponse, dans `Dispatcher.runForAgent` : `applyEffects` n'a pas de cas pour la commande, donc un `run` de la page n'obtient que le contrôle du cœur. Limites : un hôte doit permettre le CORS ; un téléchargement long après « Autoriser » peut finir en `page.timeout` du helper alors qu'il s'est fait (l'agent vérifie avec `track.get`) ; un hôte `https` du réseau local reste joignable si l'utilisateur l'autorise, comme pour `project.open_url` (il voit l'hôte).
- **Parité page/helper.** Le helper exécutera le même crate en natif pour l'import natif (#778, laissé hors d'AU-7). Pour le même blob, le PCM natif et le PCM WebAssembly sont identiques au bit près pour le WAV, l'AIFF, le FLAC, l'ALAC, le Vorbis et l'Opus ; pour le MP3 et l'AAC, qui passent par `powf` et `cos`, dont le dernier bit diffère entre la bibliothèque C native et celle de Rust en WebAssembly, ils diffèrent de 3,3·10⁻⁷ au plus (−130 dBFS), sous la tolérance de parité du banc de rendu (10⁻⁵).
- **Boost.** Depuis BO-1, la page écrit le dossier dans les deux modes. L'import tourne donc dans la page en Boost aussi, et rien du fichier ne traverse le WebSocket (mesuré : un import d'une heure en Boost envoie 32 octets au helper, aucun échantillon). Depuis AU-7 (#116), le helper lit les blobs et les caches que la page a écrits pour jouer les clips audio en natif (§ 5.13).

### 5.10 La bibliothèque de presets (#191)

Les presets d'un projet sont des fichiers de son dossier (`presets/<id>.json`, [modèle de projet](02-modele-projet.md) § 2.8), écrits avec le reste du projet par le même chemin, fichier par fichier et de façon atomique. La bibliothèque de l'utilisateur, disponible dans tous les projets, vit ailleurs :

- **Où** : `faulk/presets/<id>.json` dans l'OPFS du site, un fichier par preset, au même format. Même origine en mode Web et en mode Boost, donc la même bibliothèque dans les deux.
- **Pourquoi l'OPFS** : la bibliothèque doit être joignable depuis tous les projets et tous les navigateurs sans clic. Un agent qui enregistre un preset n'a pas de geste de l'utilisateur, et une poignée de dossier réel perd sa permission à chaque rechargement (il faut un clic pour la rendre) ; Firefox et Safari n'ont pas de sélecteur de dossier. L'OPFS ne demande aucune permission, existe dans tous les navigateurs que Faulk sert, garde déjà les projets du navigateur (§ 5.8), et garde les fichiers au même format texte (pas IndexedDB) : exporter la bibliothèque plus tard est une copie.
- **Ce que ça coûte** : la bibliothèque n'est pas un dossier visible ; elle est propre à un profil de navigateur (absente sur une autre machine) ; un navigateur peut l'évincer si `persist()` est refusé (le même avertissement que pour les projets du navigateur) ; sans `createWritable` (Safari avant 26) elle ne vit que dans l'onglet. Une bibliothèque dans un vrai dossier (par un sélecteur, ou par le helper quand il écrira de nouveau sur disque) et son export restent à faire.
- **Dans le cœur** : la page lit les fichiers et les donne au cœur (`pw_stage_library`), qui les tient dans son état (`State::library`) pour que les commandes `preset.*` la changent comme une édition annulable ; un fichier illisible est laissé de côté, nommé dans le rapport, jamais supprimé. Un changement de la bibliothèque n'est pas un changement du projet (aucun enregistrement automatique du projet pour lui) : la page demande au cœur les octets canoniques du preset touché (`pw_preset_file`) et écrit ou supprime son fichier (`createWritable` ne remplace la cible qu'à `close()` : un onglet fermé pendant l'écriture laisse l'ancien fichier intact).
- **Dans la page** (`web/src/lib/storage/presets.ts`, `Dispatcher`) : la bibliothèque est lue quand le cœur est créé, quand la page revient au premier plan et quand un autre onglet annonce un changement (`BroadcastChannel` `faulk.presets`). Les écritures passent une à une dans une file ; une relecture n'est donnée au cœur que si aucune écriture n'a commencé ni fini pendant qu'elle lisait (sinon elle relit une fois les écritures faites) : le preset qu'une commande a enregistré ne disparaît pas. Une écriture refusée (quota, stockage indisponible) affiche un avis s'il n'y en a pas déjà un, le preset reste dans l'onglet et l'écriture est retentée au retour de la page ou au prochain changement annoncé ; l'avis s'efface quand elle réussit. La première écriture demande `navigator.storage.persist()`, pour que le navigateur garde la bibliothèque même à qui ne travaille que dans un vrai dossier. Seuls les fichiers nommés par un identifiant de preset sont lus ; les autres ne sont jamais touchés. Un fichier vide laissé par une écriture interrompue avant sa première fermeture est écarté à la lecture et remplacé par la prochaine écriture de ce preset.
- **L'en-tête du panneau d'un device** (`web/src/views/devices/PresetBar.svelte`) : précédent / suivant (les presets chargeables du type, usine puis projet puis bibliothèque), le nom du preset affiché (son nom actuel s'il est là, sinon celui que le device a retenu), une marque « modifié » (réponse de `preset.list`), et un menu : enregistrer dans le projet ou dans la bibliothèque (un champ de nom), copier dans la bibliothèque, renommer, supprimer. Chaque geste est une commande `preset.*`.

**Mode Boost** : depuis BO-1 (#102, protocole 23) le helper ne tient aucun projet ; c'est la page qui écrit le dossier du projet dans les deux modes. Depuis AU-7 (#116), le helper ne lit dans ce dossier que les fichiers audio (§ 4, § 5.13). Rien des presets ne traverse le lien page ↔ helper.

### 5.11 Lecture des fichiers audio depuis le disque (AU-3, #112)

Ce qui est écrit dans `crates/engine/src/audio_source.rs`, `crates/engine-wasm` (`fk_disk_*`) et `web/src/lib/audio/stream/`. Le code fait foi. Depuis AU-4 (#113), les voix sont celles du lecteur de clips audio (`crates/engine/src/devices/clip_player.rs`, dernier point de cette section) ; la voix de test de l'hôte (`Host::probe_*`) ne sert plus qu'aux tests natifs de la couche de flux (fonction `testing`) et a quitté le module livré (`fk_probe_*` retirés).

- **Sources.** Chaque média qu'un clip audio du moteur utilise est une source (`AudioSourceDeclare`, avec l'empreinte SHA-256 du blob). Le moteur ne lit rien lui-même : son côté préparation (le planificateur `Disk`) produit des **lectures par plages** (octets d'un fichier), l'hôte les fait et lui rend les octets. Il sonde d'abord la source : les 64 premiers Kio du blob, dont il tire la disposition (`PcmLayout`, désormais dans le moteur, la même conversion que celle de l'import) si elle correspond au média, sinon l'en-tête du cache PCM (`FKPCM001`, fréquence, canaux, frames, taille). Une source illisible (blob absent, cache pas encore refait, pas de disque) est **hors ligne** : comptée dans le `Feedback` (`offline_sources`) et sondée de nouveau toutes les 2 s ; sa voix se tait. Un fichier qui a changé sous la lecture (un cache refait) fait sonder la source à nouveau.
- **En mémoire.** Une source courte (≤ 30 s et ≤ 10 Mo décodés) est gardée entière ; sinon le début de chaque clip (1,5 s) et chaque boucle courte (≤ 10 s) le sont. Ces segments sont remplis entiers côté préparation, puis envoyés au moteur (`SegmentPut`) : le fil audio ne voit qu'un segment complet, et ce qu'il remplace revient par l'anneau des déchets. Tous les canaux de la source sont gardés (le choix du mixage des canaux revient à AU-4).
- **Anneaux.** Chaque piste a deux ports ; un port reçoit un anneau seulement quand une voix y lit une source qui n'est pas en mémoire, à la taille de 3 s de sa source (fréquence et canaux), et le perd après 10 s sans lecture. Le planificateur le garde 2,5 s en avance. Le protocole : la voix numérote ses demandes (génération) et les envoie par une file sans verrou ; le planificateur vide l'anneau, le marque de la génération (`ack`), puis le remplit en suivant le chemin de la demande (boucle comprise, donc sans trou au bouclage) ; la voix ne lit que les données de sa génération, et une lecture lancée pour une génération périmée est jetée à son retour.
- **Voix** (`Voice`, côté audio) : lit les segments qui couvrent sa position (départ instantané), passe à l'anneau au premier frame qu'ils ne couvrent pas (l'anneau a été demandé à partir de là au départ), garde son temps quand l'anneau manque de données (silence, puis les frames en retard sont jetés), et compte une **sous-alimentation** par bloc à court une fois l'anneau amorcé, ou après 250 ms d'attente du premier frame (un disque bloqué est compté, l'attente normale d'un saut ne l'est pas). Ni allocation, ni attente, ni panique (détecteur d'allocation dans les tests).
- **Budget.** Anneaux et segments puisent dans un budget de PCM (300 Mo par défaut, 1 Gio au plus, la marge que les limites du moteur réservent sous le plafond wasm32). Avant de charger un segment, le planificateur évince par LRU ce qui n'a pas servi depuis 5 s (les sources entières d'abord, puis les débuts de clips) ; un segment qui ne tient pas n'est pas chargé (le clip passe par l'anneau) ; un anneau n'est jamais refusé pour le budget (les tampons des voix qui jouent ne sont jamais coupés, § 5.4) : au-delà, le `Feedback` lève le drapeau de budget, et seul le plafond de 1 Gio refuse un anneau. Une voix arrêtée rend son anneau après 10 s ; une voix qui joue le garde (elle se signale chaque seconde) et en retrouve un, de la bonne forme, si elle l'a perdu. Une sous-alimentation n'est comptée que si le port a un anneau : une source hors ligne est comptée comme telle, pas comme un disque lent ; les échantillons NaN, infinis ou sous-normaux d'un fichier deviennent 0 à la conversion. L'occupation est dans le `Feedback` (`pcm_kib`).
- **Contre-pression.** Les messages du planificateur passent par la même file que ceux du projet, mais il n'en envoie plus quand cette file dépasse 64 messages (un moteur qui ne consomme pas, onglet en arrière-plan) : il ne prend jamais au projet la place qui lui rendrait `EngineBusy`.
- **Dans la page.** Le « Worker disque » est le Worker de préparation (`executor.ts`), écart à la tâche : le planificateur écrit dans la mémoire du moteur et y libère ce qui revient, et seul le fil qui tient l'instance de préparation peut le faire sans poignée de main entre deux fils ; les lectures sont asynchrones (`File.slice().arrayBuffer()`), la purge des 5 ms n'attend donc jamais le disque. Toutes les 10 ms, il demande ses lectures au planificateur, lit `blobs/<hash>` ou `.faulk/cache/pcm/<hash>.pcm` du dossier du projet (le dossier réel, ou le répertoire de l'OPFS d'un projet du navigateur), que la page lui donne à chaque rattachement. `SyncAccessHandle.read` n'est pas utilisé : il prend un verrou exclusif sur le fichier, dont le Worker du magasin a besoin quand il refait un cache ou importe.
- **Boost.** Depuis AU-7 (#116), le fil disque du helper fait les lectures du planificateur de son moteur, depuis le dossier du projet que la page a ouvert (§ 5.13). Tant que le helper n'a pas ce dossier, ses lectures échouent comme « absent » et ses sources restent hors ligne.
- **Lecture des clips (AU-4, #113).** Le lecteur de clips audio d'une piste audio a deux voix, une par port : celle qui joue et celle qui s'éteint (un changement de ce qui joue est un fondu enchaîné de 2 ms ; un troisième changement pendant ce fondu attend qu'un port se libère, 2 ms au plus). Seule exception (#704) : un placement du même clip, aux frames inchangées, qui prend la suite d'un placement là où sa voix en est (à une frame de sortie et deux frames de la source près : l'arrondi d'une coupe), sans saut du transport, comme les parties d'un placement coupé ; la voix continue sous l'identité du nouveau placement, sans fondu, et les parties jouent comme le placement entier, au bit près. Un écart plus court qu'une frame de plus de la source entre la fin d'un placement et la partie suivante de sa coupe (même clip, frames suivantes : l'arrondi de la coupe en ticks) est comblé : le placement joue jusqu'à elle ; vers un autre clip ou d'autres frames, l'écart reste. Après un changement de tempo en cours de lecture, la voix n'est plus là où la partie suivante commence (un changement de tempo ne déplace pas un clip qui joue) : cette partie entre par un fondu enchaîné, comme tout autre changement. Chaque voix rééchantillonne sa source à la fréquence du moteur (Hermite à 4 points, phase en virgule fixe sur 32 bits, identique au bit près en natif et en WebAssembly ; à fréquences égales, la sortie est l'échantillon de la source lui-même) et tire de la voix exactement les frames que sa phase consomme. Une frame que la voix n'a pas livrée (l'anneau pas encore là après un saut hors des segments résidents, une sous-alimentation) garde la dernière valeur livrée pendant qu'une porte se ferme en 2 ms, puis la porte se rouvre en 2 ms à la première frame qui arrive : ni le départ tardif d'un saut ni une sous-alimentation ne font de marche. **Latence ajoutée par le lecteur : 0 frame** (premier frame du clip à l'échantillon de son départ, rééchantillonné ou non, testé) pour un départ couvert par un segment résident ; un saut ailleurs attend l'anneau (mesures ci-dessus). En Boost, le même lecteur tourne dans le helper. Depuis AU-7 (#116), il lit ses sources dans le dossier du projet (§ 5.13). Sans ce dossier, elles sont hors ligne et les clips muets (comptés dans `offline_sources`), et le panneau Clips dit ce qu'il faut faire.
- **Export (#647).** Le rendu hors ligne de `project.export_audio` (`engine::offline`) a son propre moteur, donc son propre planificateur : le Worker d'export de la page sert ses lectures depuis le dossier du projet avec le même exécutant que la lecture (`DiskExecutor`), dans les deux modes (en Boost aussi, où les clips ne s'entendent pas encore à la lecture). Avant chaque bloc, le rendu applique ce que le planificateur a envoyé, le sonde avec sa propre horloge (les frames rendues) et ne rend le bloc qu'une fois le planificateur au repos : aucune lecture en cours ni en attente, rien à envoyer. Les débuts de clips sont donc chargés avant le premier bloc et chaque anneau est rempli à son avance de 2,5 s avant le bloc qui suit la demande de sa voix : aucune sous-alimentation, et le fichier est la lecture d'un disque qui suit, échantillon pour échantillon (testé à 0 près sur 32 s, anneau compris). Le transport ne démarre qu'après une pré-lecture de 10 ms, moteur arrêté et rien d'écrit, pour que le fondu d'entrée des pistes et devices neufs (5 ms) soit fini au premier frame, comme quand on lance la lecture d'un projet déjà ouvert. Un fichier illisible (blob absent, cache pas encore fait, lecture refusée) ne bloque pas le rendu : sa source est hors ligne, ses clips muets ; le rendu garde les médias hors ligne qu'une voix a demandés (donc joués dans la plage exportée) et la fenêtre d'export les nomme. Reste comme à la lecture : un départ qu'aucun segment résident ne couvre (un placement à un décalage dans un long média, au-delà des 16 plages préchargées d'une source) attend l'anneau un bloc, avec la porte de 2 ms.
- **Mesures** (#112, 2026-11-04, Windows 11, SSD, une machine de développement ; rien d'autre n'est affirmé) :
  - *Débit de lecture par plages*, Chromium 156 (Playwright, `web/scripts/bench-disk.mjs`), lectures de 256 Kio par `File.slice().arrayBuffer()` sur un fichier de 256 Mio : depuis l'OPFS, 430 à 600 Mo/s une lecture à la fois, 610 à 920 Mo/s à 8 en vol (la limite du planificateur), 0,5 à 1 ms par lecture à une position au hasard ; depuis un `File` du disque (un `<input type=file>`), 380 à 390 Mo/s une à la fois, 730 à 830 Mo/s à 8 en vol, 0,7 à 0,8 ms au hasard. Le fichier venait d'être écrit, donc probablement dans le cache du système : ce sont des chiffres à chaud. Le `File` d'un dossier choisi par le sélecteur n'a pas été mesuré (le sélecteur ne s'automatise pas) : le `File` d'un `<input>` est un fichier du disque, mais pas exactement le même chemin d'accès. Besoin à comparer : 48 voix stéréo 16 bits à 48 kHz lisent 9,2 Mo/s.
  - *Sous-alimentations sous charge*, natif (`crates/engine/tests/stream_load.rs`, à lancer à la main) : 48 voix sur 24 pistes, WAV 48 kHz stéréo 16 bits de 60 s, départs hors des segments résidents, blocs de 128 frames en temps réel, disque simulé qui répond à chaque lecture après 0 à 20 ms : **0 sous-alimentation sur 180 000 blocs de voix** en 10 s, avec ou sans un rendu qui occupe la moitié de chaque bloc ; premières données après 44 ms en moyenne, 83 ms au plus (les 48 voix partent ensemble). Avec un disque à 0 à 200 ms : 2 559 blocs comptés, ceux des départs qui attendent plus de 250 ms (premières données après 358 ms en moyenne, 707 ms au plus). Une première version, qui complétait chaque anneau par petites lectures, en affamait d'autres (139 425 blocs sur 180 000) : les anneaux sont désormais servis du plus vide au plus plein, par lectures d'au moins 0,5 s.
  - *Mémoire* : 55,3 Mo de PCM pour ces 48 voix (un anneau de 3 s par voix), compté dans le `Feedback` (`pcm_kib`).
  - *Latence ajoutée* : nulle pour un départ couvert par un segment résident (début de clip, source courte, boucle courte : premier frame dans le bloc du départ, testé). Un saut ailleurs attend un aller-retour du disque : 2 blocs dans le scénario déterministe (une lecture servie un tour plus tard), natif et WebAssembly identiques (même scénario, échantillons égaux au bit près), 44 ms en moyenne dans la mesure de charge ci-dessus. Mode Boost : le fil disque du helper (AU-7) suit le même planificateur, interrogé toutes les 10 ms comme dans la page, mais sa latence n'est pas mesurée (§ 5.13). Non mesuré : dans le vrai worklet de Chromium, onglet chargé.

### 5.12 Aperçus de forme d'onde (AU-2, #111)

Ce qui est écrit dans `crates/audio-import/src/peaks.rs`, `crates/audio-import-wasm`, `web/src/lib/audio/peaks/` et `web/src/lib/components/Waveform.svelte`. Le code fait foi.

- **Où et quand.** Le décodage d'un import (§ 5.9) donne aussi les crêtes du fichier, calculées par le même code Rust que le reste du pipeline, dans le Worker du magasin de projet ; elles sont écrites en dernier dans `.faulk/cache/peaks/<sha256>.peaks`, par `createWritable` (le fichier est remplacé entier à la fermeture). C'est un cache comme le PCM : nommé par le blob, jamais versionné, jamais copié par un « Enregistrer sous » ni mis dans un `.faulkpack` ; un échec de leur écriture ne fait pas échouer l'import.
- **Format.** Niveau 0 : une crête par bloc de 256 frames et par canal, le plus bas et le plus haut échantillon du bloc en deux `int8` dans [−127, 127] (127 pour 1,0), arrondis vers l'extérieur (le bas vers le bas, le haut vers le haut), si bien que l'enveloppe dessinée contient toujours chaque échantillon ; une valeur hors de [−1, 1] est écrêtée, un NaN ignoré. Niveaux 1 à 3 : blocs de 1 024, 4 096 et 16 384 frames (×4, ×16, ×64), chaque crête étant le plus bas des bas et le plus haut des hauts des quatre crêtes du niveau inférieur, ce qui est exactement la crête du bloc entier (testé). En-tête de 32 octets (`FKPEAK01`, fréquence, canaux, nombre de niveaux, frames, version du décodeur, taille du bloc de base, facteur), puis les niveaux du plus fin au plus grossier, petit-boutiste. Un fichier n'est valide que si son en-tête est exactement celui du média et de la version du décodeur, et sa taille celle qu'il annonce ; sinon il est refait.
- **Taille (mesurée).** Au niveau le plus fin, 2 octets par canal et par bloc de 256 frames : en stéréo, 45 000 octets par minute à 48 kHz et 41 344 à 44,1 kHz (test Rust sur une minute) ; les quatre niveaux font environ 1,33 fois le niveau 0 (une heure de stéréo 48 kHz : 2,7 Mo au niveau 0, 3,6 Mo en tout). Une heure mono à 16 kHz importée dans Chromium : 597 690 octets, dont 450 000 au niveau le plus fin.
- **Régénération.** Après chaque rattachement, `ensureAudioCache` vérifie aussi les crêtes de chaque média et les refait quand elles manquent ou sont douteuses, en un seul décodage avec le cache PCM s'il manque aussi ; un WAV lu directement, qui n'a pas de cache PCM, est donc décodé une fois pour ses crêtes si le projet date d'avant AU-2 (mesuré : une heure de WAV mono 16 kHz, 2,2 s depuis le rechargement de la page, pendant lesquelles les commandes répondent en 14 ms au plus). Dans la page, `PeaksCache` lit le fichier d'un média quand une vue le demande (par le Worker, jamais sur le temps du fil principal) ; absent ou douteux, il attend le travail de l'ouverture, relit, puis demande ce média au Worker (`ProjectStorage.makePeaks` : un média à la fois, arrêté quand le projet quitte sa place), et relit ; la vue dessine une ligne en attendant. Un média resté sans crêtes est retenté au rattachement suivant.
- **Dessin.** `drawWaveform` dessine sur n'importe quel canevas (le composant `Waveform`, ou une surface qui dessine plusieurs clips, comme la grille temporelle d'AU-6) : une colonne par pixel physique, au niveau le plus grossier dont le bloc tient dans une colonne, une enveloppe pleine par canal (ou les canaux réunis quand une voie ferait moins de 12 px), au moins un pixel physique de haut. Une colonne lit au plus quatre crêtes jusqu'à 65 536 frames par pixel ; au-delà, le nombre de crêtes du niveau 3 par colonne croît avec le dézoom (une heure à 48 kHz sur 1 000 px : environ onze), jamais avec la longueur du média en soi. Mesuré dans Playwright (`waveform.spec.ts`, surface de test `/dev/waveform`, une heure de stéréo 48 kHz, 360 images de défilement et de zoom couvrant les quatre niveaux, en mode strict) : 60,2 images/s, dessin moyen 0,24 ms, p95 0,38 ms. Le panneau Clips dessine, dans la ligne de chaque clip audio, la partie du fichier que le clip joue ; depuis AU-6 (#115), la case de la grille la dessine aussi, et la timeline dessine chaque placement audio dans son bloc, à travers la boucle du clip, en ne demandant à `drawWaveform` que les colonnes visibles.
- **Web et Boost.** Depuis BO-1 le helper ne tient aucun dossier : les crêtes sont calculées par la page dans les deux modes, avec le même module, et aucune ne traverse le WebSocket (testé : le même fichier importé en Web puis en Boost donne le même fichier de crêtes, et aucune trame vers le helper ne le porte). La tâche prévoyait un calcul par le helper en Boost : il n'a plus lieu d'être. Ce qui peut encore différer est la construction native du même crate (celle de l'import natif, #778 ; depuis AU-7, le helper lit le dossier mais ne calcule pas de crêtes) : pour chaque fichier de référence, les crêtes WebAssembly sont celles du natif octet pour octet (`peaks_sha256` de `expected.json`), MP3 et AAC compris, bien que leur PCM diffère de 3,3·10⁻⁷ au plus ; un tel écart pourrait en principe déplacer une crête d'un pas de quantification sur un autre fichier.

### 5.13 Le dossier du projet en mode Boost (AU-7, #116)

Ce qui est écrit dans `crates/helper/src/disk.rs`, `crates/helper/src/server.rs`, `crates/protocol` (messages `folder.*`) et `web/src/lib/stores/dispatcher.ts`. Le code fait foi.

- **La règle** (décision du fondateur, 2026-11-06) : en Boost, le helper ne lit et n'écrit que dans le dossier du projet que la page a ouvert, nulle part ailleurs. La page possède le projet : elle écrit ses fichiers dans les deux modes. Le helper ne lit que `blobs/<sha256>` et `.faulk/cache/pcm/<sha256>.pcm`, dont il construit les chemins à partir de l'empreinte du média, jamais d'une chaîne reçue. Seule exception, sa propre configuration : la liste des dossiers que l'utilisateur lui a montrés (`folders.json`, au plus 32, dans son dossier de configuration, à côté de son jeton ; décision du lead).
- **Aucun chemin ne traverse le lien.** Un navigateur ne donne jamais le chemin d'un dossier, et aucun message du protocole n'en porte un. La page envoie `folder.open { project, nonce, name }` : l'identifiant du projet, un marqueur et le nom du dossier, qui ne sert qu'au titre de la fenêtre. Le marqueur est un nombre aléatoire de 128 bits, que la page vient d'écrire dans `.faulk/link.json` de son dossier, un nouveau par dossier rattaché. Elle l'envoie après chaque `hello` et à chaque changement de place du projet ; pour un projet gardé dans le navigateur, elle envoie `folder.close`. Il arrive que le dossier refuse le marqueur, parce que l'accès n'est pas encore accordé après une réouverture. La page n'envoie alors rien au helper, le panneau Clips le dit, et elle écrit de nouveau le marqueur quand l'accès est rendu (`project.allow_access`) ou sur le bouton. Si un clic arrive pendant l'écriture qu'a lancée le rattachement, il attend cette écriture au lieu d'en commencer une autre. Le helper cherche le dossier hors de la boucle de la session, sur un fil bloquant et sans verrou. Il ne retient la réponse que si la place nommée n'a pas changé entre-temps, et il prend pour cela le verrou de la session. Le helper ouvre le dossier mémorisé qui contient à la fois l'identifiant et ce marqueur. Il répond `folder.state` avec l'un de ces états : `open`, `closed`, `unknown`, `ambiguous { count }`, `choosing`, `refused { reason }`.
- **La première fois, l'utilisateur montre le dossier.** Le bouton « Montrer le dossier… » du panneau Clips lance la commande `project.choose_helper_folder`, qui envoie `folder.choose`. Le helper ouvre alors sa propre fenêtre de dossier, une seule à la fois : la boîte commune de Windows (`rfd`), `osascript` sur macOS, `zenity` ou `kdialog` sur Linux. Il ne prend le dossier choisi que s'il contient le projet et le marqueur de la page. Sinon il refuse, avec le motif : `other_project`, `no_project`, `not_this_folder` (une copie), `unreadable`, `cancelled` ou `unavailable`. Il mémorise le dossier accepté, même si la page est passée à autre chose entre-temps, mais il ne l'ouvre que si la session et la place qu'elle a nommée n'ont pas changé. Si elles ont changé, il cherche de nouveau la place que la page nomme alors et lui en dit l'état : une demande qui a trouvé la fenêtre déjà ouverte pour un autre projet n'attend donc jamais indéfiniment. Comme toute fenêtre, celle-ci demande un clic : l'appel d'un agent sans clic reçoit un avis dans la page.
- **Deux dossiers de même identifiant.** Une copie faite hors de Faulk garde l'identifiant du projet. Le marqueur les départage : seul le dossier ouvert dans la page porte celui de la session, si bien qu'une copie que le helper serait seul à connaître n'est jamais prise pour lui. Il y a un cas où plusieurs dossiers portent le marqueur : une copie faite après son écriture. Le helper répond alors `ambiguous`, l'utilisateur choisit, et le helper ne fait jamais de choix silencieux.
- **Le confinement** (`ProjectFolder`). Un chemin donné par un appelant est d'abord contrôlé comme texte, avant tout accès au disque. Sont refusés, chacun par une erreur typée (`PathError`) : le vide, `.` et `..`, `/` en tête, `\`, `:` (lettre de lecteur, flux NTFS), les caractères de contrôle, un composant qui finit par un point ou une espace, les noms de périphérique de Windows, plus de 32 composants ou de 1 024 octets. Ensuite, le chemin canonique (liens suivis) de son plus proche ancêtre existant doit rester sous la racine canonique, et les zones réservées sont contrôlées de nouveau sur ce chemin canonique (casse, nom court 8.3, lien interne vers `blobs/`). Le fichier visé lui-même est concerné quand il existe : `PROJEC~1.JSO` est `project.json`. Un `.faulk` ou un `.faulk/tmp` qui est un lien, même vers l'intérieur du dossier, est refusé avant que rien ne soit créé à sa cible. Rien n'est gardé d'une opération à l'autre : un lien créé depuis la précédente est vu. `project.json` lui-même n'est lu que s'il est dans le dossier : un `project.json` qui est un lien vers l'extérieur ne compte pas comme un projet.
- **L'écriture** (`ProjectFolder::write`) : tous les contrôles du chemin passent avant que rien ne soit créé, si bien qu'un chemin refusé ne crée aucun dossier, pas même ses dossiers parents. Ensuite, un nouveau fichier dans `.faulk/tmp/`, vidé sur le disque, puis déplacé sur la cible. Juste avant ce déplacement, le helper vérifie que le dossier est toujours celui qu'il a ouvert : même racine canonique, même projet dans `project.json`, même dossier parent. Sinon l'écriture est refusée (`FolderChanged`) et le fichier temporaire supprimé. Si c'est le dossier entier qui a été déplacé pendant l'écriture, le fichier temporaire l'a suivi : il reste dans son `.faulk/tmp/`, que la page vide à chaque rattachement. Les fichiers du projet (`project.json`, `tracks/`, `master/`, `presets/`) et les données du dossier (`blobs/`, `.faulk/`, `.git*`) sont refusés. L'écriture se fait aussi au fil de l'eau (`ProjectFolder::begin`, puis `PendingWrite::write` et `commit`) : le fichier temporaire reçoit les octets à mesure qu'ils sont produits, et une écriture abandonnée avant son `commit` (annulée, en échec) supprime son fichier temporaire. Elle sert à l'export écrit par le helper (#319, ci-dessous) ; l'import natif (#778) s'en servira.
- **La lecture.** Le fil disque (`spawn_disk`) interroge le planificateur du moteur du helper toutes les 10 ms. Il fait les lectures hors du verrou du moteur et rend chaque réponse au moteur qui l'a demandée, et seulement à lui : un moteur installé entre-temps, pour une autre sortie, numérote ses lectures à partir de 1 lui aussi. Il suit les règles de l'exécutant de la page (`DiskExecutor`) : une lecture commencée dans un dossier remplacé depuis répond « absent » ; un fichier qui a changé entre deux lectures (longueur ou date) répond `Changed`, et le planificateur le sonde de nouveau ; une lecture est plafonnée à 16 Mio et une lecture au-delà de la fin est courte. Le dossier se ferme avec la session, quand elle se termine ou est remplacée. Il se ferme aussi dès que la page nomme une autre place (un autre projet ou un autre marqueur, même si sa fenêtre de dossier est ensuite annulée), ou que son marqueur est refusé : le helper ne lit jamais le dossier d'une place que la page a quittée.
- **L'export audio écrit par le helper** (#319). La page construit toujours le travail d'export (`commands::export::job`, les trois flux du moteur que rend aussi son Worker) et l'envoie au helper : `export.start { id, project, name, sample_rate, bits, body_frames, setup, start, stop }`, les flux en base64 dans un message JSON (les trames binaires restent les flux du moteur en direct). Le helper rend ces flux avec `engine::offline`, le même code que le Worker, sur un fil à lui et avec un moteur neuf : jamais le moteur en direct, jamais un fil audio ; ce fil a une priorité sous la normale sous Windows. Les lectures des clips audio sont servies depuis le même dossier, par l'empreinte. Le fichier va dans `exports/<nom>.wav` du dossier ouvert, par l'écriture confinée au fil de l'eau ; un fichier déjà là est gardé, et le premier nom libre `<nom> (2).wav`, `<nom> (3).wav`… est pris, par un déplacement qui refuse de remplacer (`MoveFileExW` sans remplacement sous Windows, un lien dur sous Unix), si bien qu'un fichier apparu pendant l'export est gardé lui aussi. Le helper répond `export.progress` (au plus toutes les 100 ms), puis `export.done` (le chemin dans le dossier, la taille, les mesures du rendu) ou `export.failed` avec un code : `export.busy` (un export à la fois), `export.no_folder` (aucun dossier ouvert pour ce projet), `export.invalid`, `export.render`, `export.write`, `export.folder_changed`, `export.cancelled`. La page ne passe par le helper qu'en Boost, quand le helper annonce `export` et a ouvert le dossier du projet (`folder.state` `open`), et que les flux tiennent dans 64 Mio (`MAX_EXPORT_STREAM_BYTES`) ; sinon elle rend dans son Worker avec la boîte de dialogue du navigateur, comme en Web, où rien ne change. Le nom vient du champ de la boîte de dialogue : la page le nettoie à la règle du helper (au plus 120 octets, les noms de périphérique de Windows préfixés d'un `_`), et le helper le contrôle de nouveau : un seul composant, aucun caractère refusé par Windows (`<>:"/\|?*`), puis le contrôle de texte de l'écriture. **Menaces et gardes** : un nom qui sortirait d'`exports/` (`..`, `/`, `\`, `C:`, flux NTFS, périphérique) est refusé avant tout accès au disque ; un `exports` qui est un lien vers l'extérieur (`Escapes`) ou vers `blobs/` (`Reserved`) est refusé ; une annulation, la fin ou le remplacement de la session, ou un autre dossier ouvert pendant le rendu (une autre place nommée, `folder.close`) arrêtent l'export sans rien laisser, pas même le fichier temporaire ; le même dossier nommé de nouveau (la page envoie `folder.open` après chaque `hello`, donc après un changement de sortie) est le même dossier, comparé par sa racine canonique et son projet ; un dossier déplacé ou remplacé sur le disque juste avant le déplacement final donne `export.folder_changed`. Le balayage de `.faulk/tmp/` par la page à chaque rattachement laisse un fichier `helper-*.tmp` modifié depuis moins de 10 minutes : un export en cours l'écrit à chaque pas de son rendu. **Limites** : sur un disque sans liens durs (FAT, exFAT) hors de Windows, le nom libre est vérifié puis le fichier déplacé, en deux temps ; la charge d'un export sur la sortie en direct n'est pas mesurée.
- **Limites acceptées.** Un processus local qui remplace un lien juste entre le contrôle et l'ouverture peut détourner une lecture ou une écriture. Ce processus a déjà les droits de l'utilisateur sur le dossier, et le contrôle refait juste avant le déplacement réduit la fenêtre. Un lien dur est le même fichier, et son chemin ne permet pas de le distinguer. Une écriture remplace l'entrée par un déplacement, elle n'écrit jamais à travers le lien. Une lecture ne sert que le moteur : aucun contenu de fichier ne retourne à la page. La fenêtre de dossier native n'est testée qu'à travers une doublure (`FolderPicker`) : le chemin `rfd` est compilé sur Windows par la CI, ceux de macOS et de Linux ne sont pas vérifiés à la main.
- **Tests.** L'attaque de chaque garde est dans `crates/helper/src/disk/tests.rs` : chaque forme de chemin refusée, une liste du dossier et un témoin extérieur inchangés, les jonctions et les liens symboliques qui sortent, un dossier remplacé avant le déplacement, une lecture qui finit après un changement de dossier, une réponse qui arrive après un changement de moteur. Les messages et la lecture des clips sont dans `crates/helper/tests/folder.rs`, sur de vraies connexions. Un clip y est muet sans dossier et joue avec, et aucun morceau de 32 octets du blob (du bruit) ne paraît dans une trame. Deux dossiers du même projet donnent une question. Une réponse de la fenêtre qui arrive après que la page a changé de projet n'ouvre rien. Les messages sans jeton, d'une autre origine ou sur le lien de contrôle sont refusés sans ouvrir de fenêtre. Côté page : `native-engine.test.ts`, `dispatcher.test.ts`, `storage.test.ts`, `backend.test.ts` (le marqueur ne compte jamais comme une modification du dossier) et `boost-folder.test.ts`, plus l'e2e `helper.spec.ts`. L'export (#319) : les noms hostiles, l'écriture abandonnée, le nom libre et le déplacement sans remplacement dans `disk/tests.rs` ; dans `crates/helper/tests/export.rs`, sur une vraie session, la parité du fichier écrit par le helper avec celui du Worker (le module WASM, à `PARITY_TOLERANCE`), une annulation, un dossier changé, la même place nommée de nouveau, une page partie pendant le rendu et chaque refus ; côté page, `audio-export.test.ts`, `helper-export.test.ts`, `backend.test.ts`, `dispatcher.test.ts`, `native-engine.test.ts` et l'e2e `helper.spec.ts`.

## 6. Décisions du fondateur (2026-10-14) et questions restantes

Décidé :

1. **Isolation cross-origin** (COOP/COEP, ou Document-Isolation-Policy dans Chrome) : acceptée, mise en place par la tâche AU-0 dès la phase 0, avec ressources auto-hébergées et prudence avec les fenêtres d'authentification d'autres origines.
4. **Firefox et Safari** : l'OPFS + export en archive suffit pour le MVP ; le helper reste le moyen d'avoir un dossier réel partout.

Choix techniques, tranchés dans les tâches du [découpage du MVP](../specs/02-decoupage-mvp.md) :

2. Fréquence d'échantillonnage : rééchantillonnage **à la lecture**, dans le moteur (§ 5.3, tâche AU-4) ; pas de fréquence de projet fixe.
3. PCM décodé d'un fichier compressé : second blob versionné, ou cache régénérable ? Proposition retenue par défaut : cache régénérable dans `.faulk/cache/`, le blob gardant les octets d'origine ; la PR d'AU-1 présente ce choix et son coût au fondateur. Mis en œuvre par AU-1 (#110, § 5.9) : `.faulk/cache/pcm/<sha256>.pcm`, sauf pour un WAV ou un AIFF lu directement, qui n'en a pas.
5. En mode Boost, qui ouvre le projet : le sélecteur natif du helper ou le rapprochement par identifiant ? Tranché par AU-7 (#116) : les deux. La fenêtre de dossier du helper sert la première fois. Ensuite, le helper reconnaît le dossier par l'identifiant du projet et par un marqueur que la page écrit (§ 5.13).
6. Débit réel de lecture par plages (File System Access et OPFS) et latence de démarrage d'une voix : **à mesurer**, tâches AU-3 et AU-8.
7. `FileSystemHandle.move()` sur un dossier choisi par l'utilisateur : comportement à vérifier dans Chrome stable, tâche SV-2.
