# Verification before ending a task

Tests passing is not enough to call a task done. Run the checks of every area the task touches. The commands below are the target; they become real as the first spike creates the workspace. Update this file in the task that changes them.

## Rust (any change under `crates/`)

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build -p engine-wasm --target wasm32-unknown-unknown --release
cargo build -p project-wasm --target wasm32-unknown-unknown --release
```

The folder format of the project (`crates/project/src/file/`, SV-1): `cargo test -p project` runs its tests (reference folders `tests/reference/`, the documented examples, generated projects, errors, migrations, pack). The reference folders are rewritten with `FAULK_BLESS=1 cargo test -p project --test folder_reference` (review the diff against `docs/architecture/02-modele-projet.md` § 2.3 to § 2.5 before committing it). The time-bounded fuzz of the files, the snapshot and the pack (`folder_errors`) prints its seed; `FAULK_FUZZ_SEED=<n>` replays a run and `FAULK_FUZZ_SECS=<s>` lengthens it (1.5 s by default). The cost on the QA-7 profile: `cargo test -p project --release --test folder_load -- --ignored --nocapture`. Opening a project into the engine (`project.open`, SV-4): `cargo test -p commands --test project_open` (refusals, session, history, every `FileError` mapped), `cargo test -p test-support --test open` (render identical after save and open, nothing of the old project keeps sounding, the solo comes back from the session file and is in no versioned file; native and WASM parity), `cargo test -p project-wasm` (the folder frame and staged blobs), and the whole path on the QA-7 profile, `cargo test -p project-wasm --release --test large -- --ignored --nocapture` (stage, read, snapshot and encode in Rust on memory: no storage, no JavaScript). In the web app, `pnpm test` runs the folder through the real core (`core.test.ts`, `dispatcher.test.ts`) and `open-project.spec.ts` (dev project only, `__faulkOpen`) opens the reference folder in the page. Saving into a folder (SV-2): `cargo test -p project-wasm` (the save frames: only what changed, pending until reported, a copy's new identity, the files of an opened folder left alone), `cargo test -p commands --test project_store` (`project.new`, `project.save`, `project.save_as`, what `project.open` leaves for a save), and the cost on the QA-7 profile, `cargo test -p project-wasm --release --test large -- --ignored --nocapture` (save as, autosave after an edit, a forced save with nothing to write). In the web app `storage.test.ts` runs the controller (autosave timing, permission, failures, opening, new, external edits, the start of a page) against stand-ins, `backend.test.ts` the folder over a directory in memory (atomic writes, failures), and `project-store.spec.ts` the whole thing in Chromium with a simulated `showDirectoryPicker` that hands back an OPFS directory: a native folder dialog cannot be driven headless, so the behaviour of `createWritable` and `move()` in a folder the user chose is checked by hand in Chrome and Edge. `project-save.spec.ts` (dev project only) prints the cost of an autosave on a project of 25 600 notes and the gaps between the engine's reports while it plays. The browser's own storage and `.faulkpack` (SV-3): `cargo test -p project-wasm` (the pack out and back, refusals, a save cut short at every file still opens, a session change is not a project change), `storage.test.ts` (the draft, Save as from a draft, the start of a page, delete, export, import, a full quota), `opfs.test.ts` (the OPFS listing, the sweep of half-made directories, `persist()`), and `browser-storage.spec.ts` in Chromium (draft and reload, Save as, a browser with no folders, export then import into a folder byte for byte, a full storage through the browser's quota override); Firefox and Safari are not run. The commands for the page's storage actions (#323): `cargo test -p commands` (`contract.rs` examples and refusals, `project_store.rs` for `project.list_stored`), `cargo test -p project-wasm` (`pw_stage_stored`), `storage.test.ts` (every guard: no conflict, a conflict settled while the question is open, no click, a name the page did not list, a write held by an open question), `dispatcher.test.ts` (each command reaches its storage action, also before any core exists and in Boost), and `storage-commands.spec.ts` (dev project only: the commands sent with no click, like an agent, then the same actions clicked, English and French).

## Engine and modules

- **Offline render tests**: render a known input through the engine or module without an audio device, and assert on the signal: peak and RMS level, expected spectrum (FFT bins), silence where silence is expected, no NaN, no infinity, no denormals.
- **Render harness** (`crates/test-support`, QA-1): build the project through commands, render it, assert on the signal. A `Session::single_synth()` (or `Session::from_state(state, ctx)`, which starts with a `Reset` and the snapshot of that project) runs each command (`note_on`, `note_off`, `set_param`, or any `Command` with `run`, or `exec` for its output) on a real project state, so a refused command fails the test, and records the engine messages of each outcome (`commands::engine_msgs::compile`, PR-3) plus the blocks to render (`render_secs`, `render_blocks`) as a `Scenario`; `resync` sends a new snapshot. Raw engine messages go in with `messages`. `EngineView::of_stream(scenario, &ctx.engine)` folds a scenario's messages into the engine's control state named by ids, and `EngineView::of_project` builds the same view from a project without the compiler: live commands and a snapshot must give the project's view (`crates/test-support/tests/compiler.rs`). Then:
  - `render_native(&scenario)` renders through `engine::host`; both flush the prepare side before each block and panic on a rejected, skipped or still pending message; `render_wasm` through the `wasm32-unknown-unknown` build of `engine-wasm` in an interpreter (built into `target/parity`; not the shipped `wasm32-wasip1-threads` module, which the web tests run); `parity(&scenario)` does both, asserts they agree within `PARITY_TOLERANCE` (1e-5) and returns the native render.
  - On the `Render`: `peak`, `rms` (whole render or `_in(start..end)` seconds), `assert_finite`, `assert_no_denormals`, `assert_clean` (adds full scale), `assert_silent(window)` (exact zeros), `assert_audible`, `onset(threshold, from)` and `assert_onset_at`, `spectrum(window)` (`dominant_hz`, `peak_in(band)`), `assert_close`, and `write_wav(name)` for `.qa/renders/<name>.wav`. Note (#402): the output protection is the last stage of `Engine::render`, so on a render that went through it `assert_finite` and the full-scale part of `assert_clean` pass by construction (a NaN is silenced, a runaway clamped); `assert_no_denormals` is unaffected. `render_native` asserts `engine.limiter_silenced() == 0` for you, so a NaN on a non-device path (master strip, automation, summing) still fails; a rig that drives `Engine`/`Host` directly must assert `limiter_silenced() == 0` itself, and a per-device NaN test must render the device directly (`device.process`), not through the engine.
  - Reference projects: `test_support::reference::ALL`, built by functions in `reference.rs` and recorded in `crates/test-support/tests/fixtures/<name>.stream`; `reference::load` fails when a fixture is stale. After a change of the command layer's mapping, `FAULK_RECORD=1 cargo test -p test-support` rewrites them. A new reference project (audio, automation: AU-8, AM-6) is a function added to `ALL` plus its recorded fixture.
  - A crate uses it with `test-support = { path = "../test-support" }` in `[dev-dependencies]`; examples: `crates/engine/tests/project_render.rs`, `crates/engine-wasm/tests/project_parity.rs`.
- **Export audio** (`project.export_audio`, #297): `cargo test -p test-support --test export` renders songs built by commands through `engine::offline` and reads the WAV back (header, length, level, tail under -90 dBFS and its 30 s cap, loop region, formats and rates, the output protection holding every format under -0.3 dBFS with the reported gain reduction on a hot mix (#402), the metronome never in the file, determinism); `cargo test -p test-support --release --test export -- --ignored --nocapture` prints the render time of a three-minute song; `cargo test -p engine-wasm --test export_parity` (slow: an interpreter) compares the native and WASM files and the gain-reduction stat on a hot mix; `cargo test -p commands --test contract` covers the command (examples and refusals), `cargo test -p project-wasm export` the job. In the web app `export-render.test.ts` runs the shipped engine module and the project core under Node, `audio-export.test.ts` the dialog's controller against stand-ins (cancel at each point, every failure), `ExportDialog.test.ts` the dialog's limiter-pushed warning threshold, and `export-audio.spec.ts` the whole thing in Chromium with a simulated `showSaveFilePicker` (an OPFS file): header, length, not silent, the live song still playing meanwhile, the download fallback, French, a hot mix warned and held at the ceiling, and in the dev project the command and the three-minute song. The real save dialog cannot be driven headless: it is checked by hand in Chrome and Edge.
- **Real-time safety**: the audio path runs under the allocation detector in debug; a test renders several seconds of audio with parameter changes and MIDI events and must not trigger it.
- **Parity**: the same render through the native build and the WASM build gives the same output within a stated tolerance.
- **Listening**: when a change affects the sound, write the render to a WAV file under `.qa/renders/` and tell the user where it is. Never claim something "sounds right": only the user judges by ear.

## Commands and agents (any change under `crates/commands` or to the MCP and ACP bridges)

- Each new or changed command: schema, description and undo covered by tests. Add one example of the command, with the state it runs from, to `examples()` in `crates/commands/tests/contract.rs` (the catalog test there proves its description and both schemas; the harness `commands::testing::check` proves the metadata rules and the undo: apply, undo restores the state, redo), and one `check_refusal` case per refusal of the command (the state stays intact). A declared command without an example fails the tests.
- The parity test passes: every command is exposed as an MCP tool, and no MCP tool exists without its command.
- Drive the change from a real agent: connect Claude Code to the helper's MCP server and run the command, then check the result in the page and in the history (author shown, undo works).

## Web UI (any change under `web/`)

**One command** (#372): `node scripts/agent/verify.mjs`, from the repository root (Git Bash, PowerShell or Linux), runs `pnpm format:check`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, then the `dev` end-to-end specs that the diff against `origin/develop` (committed, staged, unstaged and untracked files) can affect, then the smoke tests of the other specs (below). The specs come from an explicit table, file to specs, in `scripts/ci/e2e-plan.mjs`, the same table and the same plan as the CI (#377: `planE2e`). A file of the page that the table does not name (stores, engine, i18n, components, styles, generated types, config), a crate, the `Cargo` files or `tests/e2e/support.ts` run the whole suite; so does an unknown path, or a table that names a spec that no longer exists. Docs, notes, unit tests and scripts (except `scripts/ci/`, which holds the table and the selection: the whole suite) need no browser test. The script picks three free ports for the dev server, the preview server and the stand-in helper (`--ports dev,preview,helper` forces them), so two checkouts never collide, and ends with a short summary (ok or fail per step, specs, durations); the output of a step is shown only when it fails (`--verbose` streams it). Options: `--fix` (applies the auto-fixable lint with `pnpm lint --fix`, then rewrites the formatting with `pnpm format`, instead of failing on them; lint errors that cannot be fixed still fail the step), `--base <ref>`, `--all` (whole suite), `--no-e2e`, `--dry-run` (prints the selection, runs nothing), `--keep-going` (do not stop at the first failure), `--clean` (afterwards removes `web/test-results`, `web/playwright-report` and `web/.svelte-kit`; `node_modules` and the build cache stay). It runs neither `pnpm build` nor the `preview` project: for a change that can alter the production build, use the list below. When you add a spec or move a feature, update the table; `node --test scripts/ci/e2e-plan.test.mjs` fails if the table names a spec that does not exist, or if a spec on disk is neither named by an area rule nor in the test's list of whole-suite-only specs (CI runs it with the agent scripts: run it yourself when you add, rename or delete a spec; a stale table still falls back to the whole suite, it only loses the saving). The script stops its child processes (the whole process group on Linux, `taskkill /T` on Windows) when interrupted.

Shared build cache: the script builds Rust into one directory for every checkout (`CARGO_TARGET_DIR`; default `%LOCALAPPDATA%\faulk-build\target` on Windows, `$XDG_CACHE_HOME/faulk-build/target` or `~/.cache/faulk-build/target` elsewhere) with `CARGO_INCREMENTAL=0`, so a new worktree does not rebuild every dependency. The bound is 8 GB (`FAULK_BUILD_CACHE_MAX_GB` changes it). Past it the summary ends with a WARNING line; the script never deletes on its own, because a delete under another checkout's running cargo breaks that build. `node scripts/agent/verify.mjs --prune-cache` empties the directory (always, before the build), so run it when no other build is running (a delete under a running cargo breaks that build). `FAULK_SHARED_TARGET=0` keeps the checkout's own `target/`; a `CARGO_TARGET_DIR` you set wins. When `origin/develop` cannot be read (never fetched), the script runs the whole suite and says so: `git fetch origin develop` first. `web/scripts/build-wasm.mjs` asks `cargo metadata` where the output is, so it follows any of these. Cargo locks the directory while it builds, but the artifact it leaves has the same path for every checkout, so `build-wasm.mjs` and `build-proto.mjs` hold a second lock (`web/scripts/target-lock.mjs`, a `.faulk-build.lock` folder in the target directory, stale after 15 minutes) around "build, then copy": two checkouts building at once wait for each other, and each copies its own build. The pnpm store is already shared by every checkout on a drive (hard links), so keep the worktrees on the drive of `pnpm store path`; the store has no size limit of its own, `pnpm store prune` drops the packages no checkout uses (run it when the disk is short). To free the disk: delete `%LOCALAPPDATA%\faulk-build`, `web/node_modules` and the worktree.

The commands one by one:

1. In `web/`: `pnpm gen:check` (regenerates `src/lib/generated/`, fails on a diff; `dev`, `build` and `test` regenerate it too), `pnpm format:check`, `pnpm typecheck`, `pnpm lint`, `pnpm test` (builds the wasm engine and runs it under Node), `pnpm build`, then `pnpm test:e2e` (Playwright, `web/tests/e2e/`: starts its own dev server on 5180 and a fresh build under the preview on 4180, never reuses one; cross-origin isolation, helper sockets against a stand-in helper on 47800, which must be free (`FAULK_E2E_HELPER_PORT=<port>` moves it, page included, when an installed helper holds it); `FAULK_E2E_DEV_PORT` and `FAULK_E2E_PREVIEW_PORT` move the 5180 and 4180 servers when another checkout holds them; the e2e build sets `VITE_FAULK_DEV_ROUTES=1`, which makes the test surfaces under `/dev` (the time grid's, AR-3) show their content, empty in a production build), simulated Web MIDI, the landing page). `FAULK_E2E_CHANNEL=chrome` or `msedge` runs it in the installed Chrome or Edge; the first run needs `pnpm exec playwright install chromium`.
2. Start the dev server (`pnpm dev`, port 5173): the landing page is at `/` (`/en`, `/fr`) and the DAW at `/app`. Check the landing page with Playwright at 1440 and 390 px in both languages (no horizontal scroll, keyboard focus, no request to another host, no JavaScript loaded besides the lazily loaded animation chunk `landing/anim.*.js`, no wasm). The sound objects' animation (`web/src/lib/landing/anim/`): six `.is-live` stages, no console error, a still frame under `prefers-reduced-motion: reduce`, no rendering while off screen or in a hidden tab, axe 0 violation, and frame times measured while hovering the hero and the library (`?fk-anim-t=<s>&fk-anim-p=<x>,<y>` gives a reproducible frame for screenshots). Open the DAW (`/app`) with Playwright. 3. Explore beyond the scripted flow: double clicks, reload during playback, helper connected then disconnected, tab in the background.

### Timing budgets of the e2e specs

`engine-mo2.spec.ts` (the shipped worklet) measures the cost of the engine channel on the render thread of a real AudioWorklet: 2 µs per pumped message and 500 µs for the longest pump (the swap of a table at its limit), budgets of CT-3 and MO-2. `engine-channel.spec.ts` is the CT-3 prototype, kept as the evidence of the chosen way (and of way (a), which was not shipped); it holds ceilings only, in every mode (10 times 2 µs and 500 µs, and 500 µs per message for a burst of way (a), whose own bound is 50 µs). Every number is printed, with the mode (`timing: ceiling…` or `timing: STRICT…`); in strict mode each of the five runs is printed and checked, then the asserted medians.

- **CI and default**: the assertions hold a ceiling ten times the budget (20 µs per message, 5 000 µs for the longest pump). A shared runner is slower and noisier than a workstation (in the prototype spec (way (b), which moves 8 192 slots and a million notes in a pump) the longest pump measured 512 µs in CI run 38705342790 of `develop`, 1 049 µs in the report of #220, and up to 1 201 µs in 20 local runs on a Windows workstation that was also running other work; the shipped worklet (`engine-mo2`) measured 15 µs median and 169 µs at most over 40 such runs, and once 2.40 µs per message against a budget of 2: one preempted quantum is enough), so the ceiling only catches a gross regression (about 65 times the measured per-message cost of the shipped worklet, 280 times its longest pump), not an overrun of the budget: that is the strict run's job. The 500 µs swap of 8 192 slots and a million notes (prototype, way (b)) is held by the ceiling only; the strict run measures the shipped worklet's 2 048-entry swap.
- **Strict, on a reference machine**: `FAULK_E2E_STRICT_TIMING=1` runs the shipped measurement five times and holds the budgets themselves on the **median**. A reference machine is a workstation with nothing else running (no build, no other browser), named with its CPU and OS in the pull request; the strict run is never done in CI. Any value other than `1` or `0` is an error.

  ```bash
  cd web && FAULK_E2E_STRICT_TIMING=1 pnpm exec playwright test engine-mo2 --project=dev
  ```

  PowerShell (the variable stays set in the session, remove it afterwards): `cd web; $env:FAULK_E2E_STRICT_TIMING='1'; pnpm exec playwright test engine-mo2 --project=dev; Remove-Item Env:FAULK_E2E_STRICT_TIMING`.

The clock of these measurements (`engine-mo2.spec.ts`, `engine-channel.spec.ts` and the QA-7 bench `web/tests/bench/engine-swap.bench.ts`, #283) is a Worker spinning on a shared counter, because an AudioWorkletGlobalScope has no `performance`. That loop runs about six times slower during its first 200 to 800 ms, so each harness waits until three windows of 200 ms agree before the load starts; `engine-mo2` and the bench also convert each report at the rate measured over the window it covers (a `rate` message just before `report`) and fail when it differs by more than 25 % from a calibration taken after the load; the printed `clock … ticks/µs (check …)` shows both. Requests to the Worker and the worklet (`fixtures/measure-rpc.js`) have a deadline and reject on an error reply, a Worker error event or the node's `processorerror`, so a stall fails by name (`prepare Worker: no reply to "push" within 15000 ms`) instead of running to the test's timeout. The first pump that applies messages after a reset is printed apart (`first …`): V8 compiles a wasm function the first time it is called, on the audio thread, so that pump is cold (67 to 579 µs on the heavy project's stream, once; up to 1 367 µs in an earlier series) against 26 to 48 µs for the others. Since #355 the worklet runs `fk_warm` (`engine::warm`) in its message handler before any audio: every message of the engine goes once through a private channel (tracks, the devices of the registry, clips, an audio source, an arrangement, automation, the launch grid, the transport with sounding notes, the removals and a second `Reset`), so that V8 compiles those functions there and the first pump that applies messages is warm (the bench: median of five runs 10 µs, against 1 342 µs without the warm-up, see the QA-7 spike). `FAULK_BENCH_FIRST_MAX_US=<µs>` asserts the first pump under that figure (for a quiet machine); `FAULK_BENCH_WARMUP=0` skips the warm-up to measure the cold start again; the bench prints the time the worklet's initialisation takes with it (about 10 ms more, in the message handler, before the node is connected). `engine-mo2` asserts the longest of both because its engine has already applied the setup; the bench prints both and asserts neither unless `FAULK_BENCH_FIRST_MAX_US` is set (it then asserts the first). `FAULK_BENCH_JSFLAGS=--no-wasm-lazy-compilation` (Chromium's `--js-flags`) removes the cold pump too and tells whether a spike is a first call; `FAULK_BENCH_WARM=<n>` sends the first n pushes of the stream before the measured window (the count assertions are then off) to show what a warm-up buys.

Run it before a release and after any change to `crates/engine`, `crates/engine-wasm` or `web/src/lib/engine/worklet.ts`; report the printed numbers and the machine in the pull request.

`timegrid.spec.ts` (AR-3) scrolls and zooms the shared time grid over 200 bars for 360 frames and prints the frame interval (mean, p95, worst, share over 20 ms) and the cost of each canvas draw (mean, p95, worst). Its default ceiling (draw p95 under 12 ms) only catches a gross regression, and the frame interval is asserted in strict mode only (#284); `FAULK_E2E_STRICT_TIMING=1` holds 60 images per second (mean under 17.5 ms, under 5 % of frames over 20 ms, draw p95 under 4 ms) on one sweep, not on a median of five. A headless frame interval is locked to the display's refresh, so the draw cost is the figure that shows the headroom. Run it strict, on a reference machine, after any change to `web/src/lib/components/timegrid/`, and name the machine in the pull request.

`piano-roll.spec.ts` (PN-1) loads 2 000 notes into a clip of 50 bars through the dispatcher's dev hook (`__faulkRun`, so that test runs in the `dev` project only) and prints, with the same ceilings and strict mode as above: the cost of a drawn frame (grid plus notes, read from `data-draw-ms` and `data-body-ms` of the grid) while scrolling and zooming, the same while dragging all the notes zoomed out so that every one is in sight, and the time from calling `clip.notes.update` on all 2 000 notes to the frame that shows the result. Run it strict, on a reference machine, after any change to `web/src/views/piano-roll/` or to `TimeGrid`'s `drawBody`.

`automation.spec.ts` (AM-4) loads a lane of 10 000 points through the same hook, zooms all the way out (so that the lane is drawn as pixel columns) and prints the cost of a drawn frame (grid, clips and lane, `data-draw-ms` plus `data-body-ms`) over 240 frames of zoom and scroll, then the cost of a drawn frame and of handling one pointer move (handler, preview of the lane, effects, up to the next microtask) while all 10 000 points are dragged at once; same ceilings and strict mode as above (draw p95 under 4 ms and a move under 8 ms in strict mode). The spec also proves that the engine plays a lane: the master's level (`data-master-peak`, the engine's own report) falls when the play position reaches a volume point, whereas the knob and the fader that follow a lane show the page's reading of it. Run it strict after any change to `web/src/views/arrangement/automation/`.

Frame-rate checks on the shared runner (`grid.spec.ts` "stays fluid", `mixer.spec.ts` "render cost", `piano-roll.spec.ts`; #284): a wall-clock frame interval follows the runner (vsync, neighbours), not the code, so it is printed everywhere and asserted in strict mode only. The ceiling holds the main-thread time the page spent per frame (`mainThreadMeter` in `web/tests/e2e/support.ts`: the browser's task duration over the window), divided by the time a fixed piece of JavaScript takes on the same machine at that moment (the "reference unit"), as the best of three windows, because noise only adds time. `FAULK_E2E_CPU_THROTTLE=4` slows the page's CPU (CDP) to rehearse a slow runner; the ceilings sit 2 to 3 times above the worst value seen under that 4x slowdown and below what a 5 to 10 times heavier render costs (checked by injecting one). `keyboard.spec.ts` reads a drum hit's crest from the page (`startPeakHold`), not from a 30 Hz poll that a short sound can fall between.

Clock check of the render-thread timings (`engine-mo2`, `engine-channel`; #283, #359): the timings are read from a Worker spinning on a shared counter, and on a shared two-vCPU runner that counter's pace flips between about 55 and 110 ticks/µs within a run (CI run 40388605597), which makes the figures of the run wrong by up to as much, and taking the run again does not help there. `withStableClock` (`web/tests/e2e/support.ts`) takes a drifted run again: in strict mode up to 4 attempts, then it fails by name (a reference machine must hold its clock); otherwise 2 attempts, then the last run is kept with a printed note and held to the ceilings only, ten times the budgets, which a 2x error cannot hide a gross regression from. The budgets and ceilings are not touched, and a run whose clock held is checked against them as before, so a real regression (a busy loop in the pump, injected to check) still fails in strict mode.

The e2e build sets `VITE_FAULK_DEV_ROUTES=1`: the `preview` project is the production build plus that flag, and the `dist` folder an e2e run leaves behind has the test surfaces switched on.

## Latency (changes to audio I/O, the worklet, the helper or the protocol)

### Formatting and typed lint of the web app (#379)

What a tool does deterministically is not left to the agent.

- **Prettier** with `prettier-plugin-svelte` (exact versions in `web/package.json`; config `web/.prettierrc.json`: no semicolons, single quotes, width 160; exclusions in `web/.prettierignore`). `pnpm format` rewrites, `pnpm format:check` fails on any file it would change; the CI `checks` job runs the latter first. The one-time reformat is its own commit, listed in `.git-blame-ignore-revs`: run `git config blame.ignoreRevsFile .git-blame-ignore-revs` once per clone (GitHub's blame reads the file by itself).
- **Typed ESLint rules** (`web/eslint.config.js`, type information from `tsconfig.json` through the project service): `no-floating-promises`, `no-misused-promises`, `await-thenable`, `prefer-promise-reject-errors`, `unbound-method`, `no-implied-eval`, `no-base-to-string`, `restrict-template-expressions` and the two type-constituent rules. The `no-unsafe-*` family, `require-await` and `no-unnecessary-type-assertion` (part of `recommendedTypeChecked`) are left out on purpose: about 500 hits in all, none looked at as a bug; 76 of the `no-unsafe-*` ones are in `src/` (about 60 in `.svelte` files, where the TypeScript service types the imports of other components as `any` and `svelte-check` is the reliable check). A new `eslint-disable` needs a reason after `--`. Typed linting reads the whole program, so `pnpm lint` takes about 14 s instead of 6 to 9 s.
- **The PostToolUse hook** (`.claude/settings.json`, `scripts/agent/format-hook.mjs`, rules in `scripts/agent/format-core.mjs`): after each Edit, Write or MultiEdit it formats the touched file (`eslint --fix` then Prettier under `web/`, so that the formatter has the last word and `pnpm format:check` never fails on a file the hook touched; `rustfmt` for `.rs`; generated code, `wasm/`, `node_modules/`, `target/` and the rest are left alone) and never blocks: any error, missing tool (`web/node_modules` not installed) or timeout is swallowed and the exit code is 0. Measured on Windows: 0.2 s for a Rust or JSON file, about 3 s for a TypeScript or Svelte file (ESLint with type information starts for each file). The file on disk may therefore differ from what the agent wrote: read it again before a long edit. It does not see what a Bash command writes (`sed -i`, `git apply`, a generator): `pnpm format` and `verify.mjs --fix` are for those. `rustfmt` on a file also formats the `mod` children it declares; they are already clean since `cargo fmt --check` is a CI check, so this is a no-op in practice. Try it by hand: `node scripts/agent/format-hook.mjs <file>`.

## CI (GitHub Actions, `.github/workflows/`)

CI runs where it is useful and nowhere else (#330, founder's decisions of 2026-10-24): the code is tested once, in its pull request, and once more as a whole on the release.

| Event | What runs |
|---|---|
| Pull request against `develop` (a task) | Only what the changed files can affect, chosen by `scripts/ci/select.mjs` (below). |
| Pull request against `main` (the `develop` to `main` release, or a hotfix) | The full suite, once: workspace fmt, clippy and tests, both WASM builds, the prototype crate, the helper on Windows, the web checks with the end-to-end tests of both projects (`dev` and `preview`), the agent scripts. |
| Push to `develop` or `main` | Nothing: the jobs of `rust.yml`, `ci.yml` and `agent-scripts.yml` are skipped (`if: github.event_name == 'pull_request'`). No nightly run either. |
| Tag `helper-v*`, dispatch | `release-helper.yml`, unchanged. |

Required status checks: no branch protection or required check is configured on `develop` or `main` today (2026-10-24, `gh api repos/sprkl/faulk/branches/<branch>/protection` answers 404; the only ruleset forbids deleting branches). Should one be added, name the jobs `rust`, `helper-windows`, `web` and `agent-scripts` (`web` is the single verdict job of `ci.yml`, which waits for `select`, `checks` and the three `e2e` shards; require `web` only, never a shard): on a pull request each one always starts and reports (success when its heavy steps are skipped), so a skipped test never blocks a merge. They are skipped on a push, where nothing requires them.

### The web workflow, in four jobs (#372)

`ci.yml` has `select` (the selection above), `checks` (`gen:check`, format check, typecheck, lint, vitest, build), `e2e` (the Playwright specs, `--shard=n/N` on one to three machines (#377: none when the change touches no browser test), each with its own Chromium, dev server and helper port, a trace artifact kept 7 days on failure) and `web`, which only reports the verdict of the others (failure or cancellation of any of them fails it; a skipped job is fine). `checks` and `e2e` run in parallel, so the time is that of the slower. The common set-up (Rust targets, cache, pnpm, Node, install) is the composite action `.github/actions/web-setup`. Playwright's browsers are cached in `~/.cache/ms-playwright`, keyed on the Playwright version of `web/pnpm-lock.yaml`: a miss runs `playwright install --with-deps chromium`, a hit only `playwright install-deps chromium`. Playwright deals whole spec files out between the shards (one worker per machine, as before), so the targeted selection (`FAULK_E2E_PROJECTS`) and the full release run both shard the same way.

### The end-to-end tests of a pull request against `develop` (#377)

The `web/` files of the change go through the table of `scripts/ci/e2e-plan.mjs` (the one `verify.mjs` uses). The run is then:

- **The specs the files touch**, whole (`playwright test <specs> --shard=n/N`), plus the **smoke tests** of the other specs (a second `playwright test <specs> --grep <titles> --shard=n/N`): `isolation` (the web engine plays simulated MIDI under cross-origin isolation, the audio start), `transport` (play, stop, tempo, loop, metronome; English, 1280 px), `project-store` (edit, save as, reload, the project is found again), `open-project` (a folder opens and replaces the project), `export-audio` (a 24-bit WAV while the song plays). They cost about 30 s of tests (measured in the CI run of #380: 15 s + 2 s + 8 s + 3 s + 2 s); the list is `SMOKE` in `e2e-plan.mjs`, one title fragment per test, checked against the spec sources by the unit tests. The `--grep` list is exact: `--list` prints these five tests and no other.
- **The whole suite** (3 machines, as before) when a file is shared or unknown: the app shell, the stores, the engine and the worklet, the protocol and the generated types, i18n, components, styles, routes, `web/package.json`, the lockfile and the Playwright config, `tests/e2e/support.ts` and `fixtures/`, `ci.yml` and `.github/actions/`, `scripts/ci/`, a crate the page is built from (`engine-wasm`, `project-wasm`, `protocol` or what they depend on), `Cargo` files and `modules/`; also when a rule names a spec that no longer exists, or the list of specs on disk is empty or unreadable. The release pull request runs the whole suite on both projects, unchanged.
- **Nothing** (no `e2e` job, no machine) when no `web/` file can be seen by a browser test: docs, notes, unit tests, scripts, a change to the helper alone.
- **One table, two callers**: `verify.mjs` hands every changed file to the table, the CI only the `web/` files; the CI decides the crates itself with the Rust dependency graph (a crate the page is built from means the whole suite, `helper` alone means no browser test), where `verify.mjs`, which reads no `cargo metadata`, sends every `crates/` file to the whole suite. So `verify.mjs` can run more than the CI, never less.
- **Machines**: one per 6 spec files (the smoke tests count as one), at most 3: a machine costs about 2.5 minutes of set-up (Chromium, WASM build) against about 15 s per spec on average, but the count ignores that a spec costs between 2 s and 67 s (`transport`, `project-store`, `browser-storage`, `mixer` are the heavy ones), so a short list of heavy specs can take several minutes on its single machine.

The cost of one machine in the CI run of #380: 16 to 27 s of set-up, 25 s of Chromium, 77 to 103 s of WASM build, then 230 to 270 s of tests for a third of the suite (710 s in all). A selection of a few specs plus the smoke tests costs the set-up and about a minute of tests on one machine. A rule that sends a file to the wrong area is a hole in the net: when a bug slips through a targeted run, add the file to the table (or to `ALL`) in the fix.

### How a pull request chooses its tests

Each job starts with `node scripts/ci/select.mjs`, which lists `HEAD^1..HEAD` (the pull request merged into its base) and reads the Rust workspace with `cargo metadata --no-deps`. The rules are in `scripts/ci/select-core.mjs`, tested by `scripts/ci/select-core.test.mjs` (`node --test "scripts/**/*.test.mjs"`). A dry run needs no checkout: `node scripts/ci/select.mjs --event pull_request --base develop --files web/src/a.ts crates/engine/src/lib.rs` prints the decision (`--json` for the detail, `--files-from <file|->` for a list).

| Changed file | Effect |
|---|---|
| `docs/`, `.scratch/`, root `*.md`, `LICENSE`, `.gitignore`, issue and pull request templates, `CODEOWNERS`, `dependabot.yml` and notes under `.github/` (not `.github/actions/`), `release-helper.yml` | Nothing. |
| `crates/<name>/` | `fmt` and `clippy` on the workspace; `cargo test -p` for that crate, every crate that depends on it (normal or build dependency, transitively) and every crate that only dev-depends on one of those, so a change to `test-support` retests its users without rebuilding the page (`--workspace` when that is all of them); the WASM build of `engine-wasm` and of `project-wasm` when one of them depends on the changed code (their parity tests run with the tests); `helper-windows` when `helper` is tested; the prototype crate's fmt and clippy when `engine` changes (it depends on it from outside the workspace). The `web` job runs when `engine-wasm`, `project-wasm` or `protocol` depends on the changed code, i.e. when the page embeds the changed code or generates its types from it: a change to `helper` alone does not run it. |
| `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/`, `modules/` | All of Rust, `helper-windows`, the prototype crate and the web job. |
| `web/` | The `web` job (`gen:check`, format check, typecheck, lint, vitest, build) and the `dev` end-to-end project, only the specs and smoke tests the table gives (above); no end-to-end run when every changed file under `web/` is a `*.test.ts` outside `tests/e2e/`, a `.md`, or the formatter and lint settings (`web/.prettierrc.json`, `web/.prettierignore`, `web/eslint.config.js`). `.git-blame-ignore-revs` runs nothing. A change under `web/tests/e2e/` also runs the agent scripts job, where the table's tests check that every spec is placed. `web/src/lib/engine/proto/crate/` also runs the prototype crate's fmt and clippy; `web/vercel.json` and `web/src/lib/i18n/helper.ts` also run `cargo test -p helper` (its updater tests read them); `web/vercel.json` also runs the agent scripts. |
| `scripts/`, `.claude/` | The agent scripts (`node --test`). |
| `ci.yml`, `rust.yml`, `agent-scripts.yml` | The jobs they define, in full (for `ci.yml`: the whole end-to-end suite). |
| `.github/actions/` (the composite action `web-setup` of `ci.yml`) | Everything, as for a file the table does not know. |
| `scripts/ci/` (the selection itself and the end-to-end table), a file this table does not know, a crate directory cargo does not list | Everything, as for a release. |

Fail safe: if the file list or the workspace cannot be read (or is empty), the decision is "run everything"; an unknown path never skips a test. A path that a job reads but the table skips lets a broken change through green: add it to `select-core.mjs` and its test in the change that makes the job read it.

Consequences for the lead and for local work:

- A merge does not rerun anything, so two pull requests that are green apart and red together (#273, #303) are caught only if the second one was tested on the current `develop`: before merging, the lead updates a pull request that is behind (`gh pr update-branch`) and waits for its targeted CI (`issue-tracker.md` > Merge and close).
- The `preview` end-to-end project and the cross-crate parity of an unrelated crate run only on the release pull request. `FAULK_E2E_PROJECTS=dev` (or `preview`) runs one project with its server only; unset, both. The `dev` server does not build the WASM: run `pnpm build` first, as CI does. For a change that can alter the production build (vite config, `vercel.json` headers, adapter, the landing page), also run `pnpm test:e2e --project=preview` locally before the pull request.
- The helper trial build (`release-helper.yml`) no longer follows a merge to `develop` or `main`: a dependency bump in `Cargo.lock` is built and tested on Linux and Windows (`rust`, `helper-windows`) in its pull request, but packaged on macOS only by the next `helper-v*` tag build.
- Back-merging `main` into `develop` after a hotfix goes through a pull request, so that it is tested like any other change (nothing runs on a push).
- Whether GitHub should require a branch to be up to date before merging (which would make the update-branch rule mechanical) is the founder's decision; it is not enabled.

`release-helper.yml` (Windows, macOS and Linux trial build) runs on a pull request only for the helper's updater, wiring and manifest, `scripts/helper-release/`, `web/vercel.json` and itself (not `Cargo.lock`: it changes for any dependency), on `helper-v*` tags and on dispatch.

After changing a workflow, lint it: `actionlint` with `shellcheck` available. To see the selection work, read the `Select the tests` step of each job in a pull request: a pull request that changes only `docs/` ends with every `heavy` output `false`, one that touches `crates/helper/` only has `rust_test=-p helper`.

## Recording the verification

Once the checks pass, record them for the current state of the code:

```bash
node scripts/agent-qa/record.mjs verified --rust "<...>" --render "<...>" ...
```

Each flag holds what was run and what came out. The flags required depend on the changed files; `record.mjs` refuses a record that lacks one and prints the full command:

| Flag | Required when the change touches | Holds |
|---|---|---|
| `--rust` | `crates/`, `Cargo.toml`, `Cargo.lock`, Rust code under `modules/` | fmt, clippy, test, WASM build |
| `--render` | `crates/engine*`, `modules/` | render tests, allocation detector, native/WASM parity |
| `--commands` | `crates/commands`, `crates/helper` | schema, description, undo, command/MCP parity, run from a real agent |
| `--web`, `--browser`, `--exploration` | `web/`, `site/` | typecheck, lint, tests; the Playwright check; the exploration beyond the script |
| `--scripts` | `scripts/`, `.claude/settings.json`, `.claude/agents/` | `node --test` and the manual try |
| `--latency` | `crates/helper`, `crates/protocol`, `crates/engine-wasm`, a `web/` path containing `worklet` | measured numbers and method, or `not measured: <why>` |

`--note` is optional. The records live outside the working tree, in the checkout's git directory: `.git/faulk-qa/` (`.git/worktrees/<name>/faulk-qa/` for a linked worktree), so `git clean -x`, a glob in the tree or a stray edit never reaches them, and each worktree keeps its own. `last-run.json` holds the verification, `history.jsonl` every record. They are written only by `record.mjs` and the hooks; the guard denies the edit tools and the shell write commands on any path through a `faulk-qa` folder.

### The Stop hook

A `Stop` hook (`scripts/agent-qa/qa-guard.mjs`) refuses to end a turn when the session's own tool calls changed the guarded code of a checkout, unless that checkout's current state has a verification record **and** its task branch has a delivery review record (`judge-dredd.md`). Its message lists the exact commands to run.

- **Guarded code**: `crates/`, `web/`, `modules/`, `site/`, `Cargo.toml`, `Cargo.lock`, `scripts/`, `.claude/settings.json`, `.claude/agents/`, tests included. Files ignored by git (`target/`, `node_modules/`, `test-results/`…) never count.
- **Fingerprint**: a hash of the content of the guarded files that differ from the merge base with `develop` (committed or not, untracked included). Any edit changes it and makes the record stale; committing does not. Without a `develop` reference, all the guarded code counts as changed.
- **Who changed the code** (a session is judged only in the checkouts where it is a *writer*):
  - Edit, Write, MultiEdit, NotebookEdit: the session becomes a writer in the checkout of the file the tool targets, when that file is guarded code. Only that file counts, so another writer's concurrent edit never does.
  - Bash, PowerShell, Agent, Task: the `PreToolUse` hook takes the state of each checkout the session works in (its current directory and the project directory) and the `PostToolUse` hook compares after the call. A call that changed the fingerprint makes the session a writer. Agent and Task calls make the lead a writer for what its subagents change during the call in the lead's own checkouts (a subagent's worktree is not measured by the lead's calls; see Limits for how the agent's own calls are attributed).
  - A checkout first seen at the end of a call (the call moved into another worktree) has no state before the call: it gets its baseline from its state after the call, and the call makes nobody a writer there. Visiting a worktree that carries another agent's work never blocks.
  - A call that moved HEAD without authoring code (reflog: checkout, switch, pull, reset, rebase, a merge of `develop` or `main`; `gh pr checkout` is a checkout) is judged only on the uncommitted changes, which such a move carries over untouched unless the call also edited them; the session's baseline then moves to the new state, and a later block message says so. Merging `develop` into a task branch brings code reviewed in its own pull request. A call that commits (`commit (merge)` after resolving conflicts included), cherry-picks, reverts or merges any other branch is judged on the whole fingerprint: that code was not verified here.
  - A call that never gets its `PostToolUse` (denied by another hook or by the user, interrupted, failed) is dropped at the next stop: it attributes nothing.
  - A session is a writer on the branch it wrote on (or the commit, on a detached head). Once it is a writer on the current branch of a checkout, its calls there are no longer measured.
- **Leaving the branch**: at the stop, each branch the session wrote on is judged where it is, not where HEAD is: with the working tree when HEAD is still on it, with its committed content otherwise. Switching to `develop` after committing leaves the branch to verify, and the message says to switch back. A stash made since the session first wrote in a checkout holds code out of the working tree: the stop is blocked until it is popped (or dropped).
- **Session baseline**: the fingerprint the first time the hooks see the session in a checkout (`SessionStart`, a tool call, or a stop). A writer whose checkout is back to its baseline (it undid its changes) is let through.
- **Checkouts**: the hook judges every checkout the session wrote to, wherever it stops; each has its own records.
- **Deferral**: to stop mid-task only to ask the user a question, run `node scripts/agent-qa/record.mjs deferred --reason "<the question>"`. It lets exactly one stop through for the current state of the code. Once used, another one is accepted only after the user writes again (the `UserPromptSubmit` hook records when), whatever the code does meanwhile. It is kept apart (`deferral.json`) and never erases a verification. Never defer at the end of a task.
- **Failure**: fail open, loudly. If the hook cannot compute a fingerprint (git missing, a repository without a commit) or its input has no session id, it lets the turn end and shows the user a warning. Claude Code also stops honouring a Stop hook after eight blocks in a row without a tool call (hooks reference, https://code.claude.com/docs/en/hooks; not measured here).
- **Guard changes**: when `scripts/agent-qa/`, `scripts/agent-review/`, `.claude/settings.json` or `.claude/agents/` differ from the merge base with `develop`, every stop shows the user a warning: the guard that runs is the modified one.

### Threat model

The guardrails exist to stop an honest agent that skips or forgets a step: ending a task without the checks, without the delivery review, or with records of an older state. They do not stop a deliberately evasive agent: one that hides a write from the hooks on purpose (an interpreter, an encoded command, a variable that expands to a path, a background process, deleting state through a path the guard does not recognise) is out of scope. Those ways around are listed below so that nobody mistakes them for protection.

### Limits

- The record holds what the lead declares: the hook checks that the fields are there, not that the checks ran.
- A change made in the very call that enters a checkout (`cd ../other && sed -i …`), or a shell write to an absolute path in another checkout, is not attributed: the hooks measure only the checkouts of the session's current directory and project directory, and that checkout has no state before the call. The next measured call there, or an edit tool on one of its files, is.
- Symbolic links are not resolved by the shell guard: a link created to point at a record or a brief (`ln -s .git/faulk-qa/review.json alias`) and then written through passes. That is deliberate evasion. `brief.mjs` never follows an untracked link, and `run.mjs` refuses to write through one.
- The records are shared by every session of a checkout: one session's deferral can be consumed by another's stop, and the last verification or review recorded wins.
- A change made by someone else during one of the session's own Bash, PowerShell, Agent or Task calls (between its two measures) is counted as the session's. Modification times cannot settle it: the change and the call overlap in time.
- Background work is not attributed: a command started with `run_in_background`, `&`, `nohup` or `Start-Process`, or a subagent run in the background, writes after its call has returned. A subagent in its own worktree writes to a checkout the lead's calls do not measure: the lead's later checkout or merge of its branch is a move, not an authoring.
- A tool outside the eight above (an MCP server that writes files) is not measured.
- Subagents share the lead's session id: the hooks of their tool calls run with it, and the hook input carries `agent_id` (documented in the hooks reference, "common input fields"). Since #392 the hooks attribute those calls to the agent, not to the lead:
  - a subagent's writer markers carry its id (`wrote-…-<agent>.json`, kept apart from the lead's), its events never write or move the session's baselines, and each of its hook events (before and after a call) refreshes an `agent-<id>.json` record;
  - the lead's `Stop` leaves a subagent's marker unjudged only while the agent is running **and** the root is a `.claude/worktrees/agent-*` folder of the same repository (same git common directory) **and** the root is not the lead's `cwd` or project directory. Anything else is judged as before: an agent writing in the lead's checkout, an agent that went quiet, a lookalike folder, any edit the lead makes itself (its calls have no `agent_id`, so its marker has none; the fingerprint then covers the whole state of the folder, the agent's work included). A subagent's marker never uses a baseline;
  - "running" means not ended, and either an event less than 20 minutes ago (`AGENT_IDLE_MS`) or a call in progress (a `PreToolUse` without its `PostToolUse`, counted for at most 60 minutes, `AGENT_CALL_MS`). An agent ends when its own stop lets it through, or when the lead's Agent or Task call that was running when the agent fired its first event returns (the hooks note the start of each of the lead's launches); an event fired later runs it again. The second signal can err toward blocking (a background agent or a parallel call caught by it is blocked until its next event; and since the hooks fire only for the eight guarded tools, an agent that only reads or thinks for more than 20 minutes looks quiet) and toward passing: an agent whose run began before the lead's call (a background agent continued in the foreground, if Claude Code reuses its `agent_id`) is not ended by that call. Ending every agent active during any foreground call would bring the false block back with every Judge Dredd call;
  - what remains exempt wrongly, and for how long: a background agent whose own `SubagentStop` did not end it (the hook did not run, or the agent was cut off), or one that ended in a foreground call that began after its run did, stays exempt for up to 20 minutes after its last event, or up to 60 minutes when its last call never got its `PostToolUse` (failed, interrupted, denied elsewhere). A lead that ends its session in that window leaves the agent's unverified work unjudged; the next stop after the window judges it. The lead's `Stop` keeps the snapshot of a running agent's call in progress (it drops the others, as before), so a change made by such a call is attributed to the agent when it returns;
  - the agent's own check: `.claude/settings.json` runs `qa-guard.mjs` on `SubagentStop` (founder's decision of 2026-10-29). Given a `SubagentStop` input (`hook_event_name`, `agent_id`) it judges only that agent's markers, without exemption, and marks the agent ended when it lets it through; a `Stop` that carries an `agent_id` without being a `SubagentStop` stays the main thread's. A subagent's stop answers only for its markers in an agent worktree of the repository: its edits in the lead's checkout are judged by the lead's `Stop`, together with the lead's own work, which the subagent could neither verify nor review. The lead's checkout is the one `CLAUDE_PROJECT_DIR` names. For a worktree-isolated subagent, Claude Code passes the lead's project there: on 2026-10-28 the lead's session held writer markers for agent worktrees, which only happens when the subagent's hooks use the lead's state root (`stateRoot` reads `CLAUDE_PROJECT_DIR` first). Were it ever the agent's worktree, the subagent's hooks would keep their markers under that worktree's own git directory (`.git/worktrees/<name>/faulk-qa`), which neither its own stop (it skips the project's checkout) nor the lead's `Stop` (another state root) reads: its work would go unjudged. A captured `SubagentStop` input (#253) would settle it. The tests feed it the input shape of the hooks reference, not a captured one: a `SubagentStop` without a valid `agent_id` judges nothing, touches no baseline or snapshot and says so in a warning, and the agent's work is then judged by the lead's `Stop` once the agent has ended or gone quiet.
- The guard reads command lines only. It removes quotes and escapes the way bash and PowerShell do (`faulk-q""a`, `faulk-\qa`, ``faulk-q`a``) before matching, but deliberate evasion passes: an interpreter (`node -e`, `python -c`), an encoded command (`powershell -EncodedCommand`), a variable or a substitution that expands to a path, or a file writer it does not know.
- A branch the session wrote on and then deleted cannot be judged: the stop lets it through with a warning to the user.
- Changing the guard is trusted only after a human reviews the pull request: the agent that edits `record.mjs` or a hook can also run the edited version. The Stop hook warns the user when the guard differs from `develop`; it cannot do more.
- The hooks run through Git Bash on Windows (`node "$CLAUDE_PROJECT_DIR/..."`). Without Git Bash, Claude Code runs hooks in PowerShell, where `$CLAUDE_PROJECT_DIR` is not expanded: the hooks then fail without blocking anything.
