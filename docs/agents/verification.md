# Verification before ending a task

Tests passing is not enough to call a task done. Run the checks of every area the task touches. The commands below are the target; they become real as the first spike creates the workspace. Update this file in the task that changes them.

## Rust (any change under `crates/`)

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build -p engine-wasm --target wasm32-unknown-unknown --release
cargo build -p project-wasm --target wasm32-unknown-unknown --release
```

**One integration-test binary per crate (#599).** Each crate's integration tests are one binary, `crates/<crate>/tests/it/main.rs`, with a `mod` per former file (`engine`, `commands`, `test-support`, `project`): a test is `cargo test -p <crate> --test it <module>::<name>`. A file in `tests/` of its own stays a separate binary only when it cannot share one: the allocation-refusing allocator of `crates/engine/tests/oom.rs` (a binary has one global allocator); the `*_cost` files of the engine (measured in release, by name, with wall-clock budgets that parallel tests would disturb, and no allocation detector); `engine-wasm`, whose parity tests each run a nested `cargo build` into its own target directory (merged, about twenty wasm builds would start at once); `protocol`, `project-wasm` (one file each) and `helper` (the helper's own task). Fixtures read from a fixed path stay in `tests/` (`crates/test-support/tests/fixtures/`, `crates/project/tests/reference/`). A new integration test is a new module of `it/main.rs`, not a new file at the top of `tests/`.

**Targeted by default (#447).** `node scripts/agent/verify.mjs` does not run all of the above on every change: it takes the files changed against `origin/develop` and applies the CI selection (`select` of `scripts/ci/select-core.mjs`, workspace read with `cargo metadata`). It runs `cargo fmt` and `clippy` on the workspace when a crate changes, `cargo test -p` for the touched crates and every crate that depends on them (dev-only users included; `--workspace` when that is all of them), the WASM builds of `engine-wasm` and `project-wasm` (whose parity tests ride with their crates' tests) only when they depend on the changed code, the prototype crate's fmt and clippy when the engine changes, and `node --test "scripts/**/*.test.mjs"` for a change under `scripts/` or `.claude/` (a few of those tests have been reported failing on Windows while CI passes; on 2026-11-01 all 444 passed locally, so a failure is yours until shown otherwise). `--full` (alias `--all`) runs the whole workspace and the whole suite; so does a base that cannot be read, a workspace `cargo` cannot read, `Cargo.toml`/`Cargo.lock`, `scripts/ci/` (except an edit of the end-to-end table alone, which runs the agent scripts, the web checks and the core tests plus the specs it newly names: Web UI > CI) and any unknown path. The helper's Windows-only job stays with the CI. `--dry-run` prints the choice. `[profile.dev.package."*"] opt-level = 1` in `Cargo.toml` optimises dependencies (notably the `wasmi` interpreter of the parity tests) in dev and test builds; workspace crates keep opt-level 0, debug assertions and the allocation detector (checked in `cargo build -v`: dependencies get `-C opt-level=1 -C debug-assertions=on`, workspace crates no `opt-level`).

A targeted run is recorded like any other: `record.mjs verified --rust "<the line verify.mjs prints>"`, which names the mode, the base, the crates and the WASM builds. The guard is unchanged: it requires the evidence flags for the changed files and ties the record to the code's fingerprint. It has never checked the content of the text (see Limits), and it still does not. The release pull request against `main` runs the full suite in CI.

## Engine and modules

- **Offline render tests**: render a known input through the engine or module without an audio device, and assert on the signal: peak and RMS level, expected spectrum (FFT bins), silence where silence is expected, no NaN, no infinity, no denormals.
- **Render harness** (`crates/test-support`, QA-1): build the project through commands, render it, assert on the signal. A `Session::single_synth()` (or `Session::from_state(state, ctx)`, which starts with a `Reset` and the snapshot of that project) runs each command (`note_on`, `note_off`, `set_param`, or any `Command` with `run`, or `exec` for its output) on a real project state, so a refused command fails the test, and records the engine messages of each outcome (`commands::engine_msgs::compile`, PR-3) plus the blocks to render (`render_secs`, `render_blocks`) as a `Scenario`; `resync` sends a new snapshot. Raw engine messages go in with `messages`. `EngineView::of_stream(scenario, &ctx.engine)` folds a scenario's messages into the engine's control state named by ids, and `EngineView::of_project` builds the same view from a project without the compiler: live commands and a snapshot must give the project's view (`crates/test-support/tests/it/compiler.rs`). Then:
  - `render_native(&scenario)` renders through `engine::host`; both flush the prepare side before each block and panic on a rejected, skipped or still pending message; `render_wasm` through the `wasm32-unknown-unknown` build of `engine-wasm` in an interpreter (built into `target/parity`; not the shipped `wasm32-wasip1-threads` module, which the web tests run); `parity(&scenario)` does both, asserts they agree within `PARITY_TOLERANCE` (1e-5) and returns the native render.
  - On the `Render`: `peak`, `rms` (whole render or `_in(start..end)` seconds), `assert_finite`, `assert_no_denormals`, `assert_clean` (adds full scale), `assert_silent(window)` (exact zeros), `assert_audible`, `onset(threshold, from)` and `assert_onset_at`, `spectrum(window)` (`dominant_hz`, `peak_in(band)`), `assert_close`, and `write_wav(name)` for `.qa/renders/<name>.wav`. Note (#402): the output protection is the last stage of `Engine::render`, so on a render that went through it `assert_finite` and the full-scale part of `assert_clean` pass by construction (a NaN is silenced, a runaway clamped); `assert_no_denormals` is unaffected. `render_native` asserts `engine.limiter_silenced() == 0` for you, so a NaN on a non-device path (master strip, automation, summing) still fails; a rig that drives `Engine`/`Host` directly must assert `limiter_silenced() == 0` itself, and a per-device NaN test must render the device directly (`device.process`), not through the engine.
  - Reference projects: `test_support::reference::ALL`, built by functions in `reference.rs` and recorded in `crates/test-support/tests/fixtures/<name>.stream`; `reference::load` fails when a fixture is stale. After a change of the command layer's mapping, `FAULK_RECORD=1 cargo test -p test-support` rewrites them. A new reference project (audio, automation: AU-8, AM-6) is a function added to `ALL` plus its recorded fixture.
  - A crate uses it with `test-support = { path = "../test-support" }` in `[dev-dependencies]`; examples: `crates/engine/tests/it/project_render.rs`, `crates/engine-wasm/tests/project_parity.rs`.
- **A big project's snapshot** (#245): a stream longer than the engine takes at once (rt ring plus prepare queue, 8 192 messages) is sent in pieces by the host's queue, `engine::host::StreamQueue` natively and `PushQueue` (`web/src/lib/engine/push-queue.ts`) in the page. `cargo test -p engine --test it stream_queue::` runs every transition of the native queue (through at once, kept while busy, a later stream behind, another stop, the bound, `clear`) with the render under the allocation detector; `cargo test -p test-support --test it big_project::` sets up, opens from a folder and resyncs a project of 6 144 clips (`test_support::big`) through `render_native` (which, like `render_wasm`, now queues a busy stream's rest) with `EngineView` equal to the project and the signal checked, plus the WASM parity of its setup; `cargo test -p helper --lib audio` the helper's setup of that project, a note played while it drains, the resync after a refused stream and the quit; `big-project.test.ts` (vitest) the page's core and `PushQueue` on the shipped engine module (setup, `project.open`, a snapshot into a suspended engine, the bound); `big-project.spec.ts` (dev project) the switch from Boost back to Web in Chromium. The time to a playable state: `cargo test -p test-support --release --test it big_project:: -- --ignored --nocapture` prints it natively, the vitest and the spec print theirs.
- **Levels for agents** (`mixer.levels`, `project.analyze_render`, #665): `cargo test -p engine --test it offline::` measures a song per track over its content only (tail excluded); `cargo test -p commands --test it levels::` covers the staging (taken once, a range that changed refused, the limit); `cargo test -p engine-wasm --test export_parity` compares the levels of both targets; in the web app `export-render.test.ts` measures through the shipped module and the core, `agents/levels.test.ts` the held meters and the Worker's cap, abort and one-at-a-time, `dispatcher.test.ts` both queries through `runForAgent`.
- **Export audio** (`project.export_audio`, #297): `cargo test -p test-support --test it export::` renders songs built by commands through `engine::offline` and reads the WAV back (header, length, level, tail under -90 dBFS and its 30 s cap, loop region, formats and rates, the output protection holding every format under -0.3 dBFS with the reported gain reduction on a hot mix (#402), the metronome never in the file, determinism); the device latency dropped from the start of the file (#755): `cargo test -p engine --test it offline::` (impulses at 44.1, 48 and 96 kHz through a Ceiling on a track, on the master, with and without the true-peak detection, the file and the levels equal to the same project without latency, a capped compensation, the allocation detector on every block) and `cargo test -p test-support --test it export_latency::` (a song through Ceilings by commands, natively and in WASM); `cargo test -p test-support --release --test it export:: -- --ignored --nocapture` prints the render time of a three-minute song; `cargo test -p engine-wasm --test export_parity` (slow: an interpreter) compares the native and WASM files and the gain-reduction stat on a hot mix; `cargo test -p commands --test it contract::` covers the command (examples and refusals), `cargo test -p project-wasm export` the job. In the web app `export-render.test.ts` runs the shipped engine module and the project core under Node, `audio-export.test.ts` the dialog's controller against stand-ins (cancel at each point, every failure), `ExportDialog.test.ts` the dialog's limiter-pushed warning threshold, and `export-audio.spec.ts` the whole thing in Chromium with a simulated `showSaveFilePicker` (an OPFS file): header, length, not silent, the live song still playing meanwhile, the download fallback, French, a hot mix warned and held at the ceiling, and in the dev project the command and the three-minute song. The real save dialog cannot be driven headless: it is checked by hand in Chrome and Edge.
- **Real-time safety**: the audio path runs under the allocation detector in debug; a test renders several seconds of audio with parameter changes and MIDI events and must not trigger it.
- **Parity**: the same render through the native build and the WASM build gives the same output within a stated tolerance.
- **Listening**: when a change affects the sound, write the render to a WAV file under `.qa/renders/` and tell the user where it is. Never claim something "sounds right": only the user judges by ear.

## Commands and agents (any change under `crates/commands` or to the MCP and ACP bridges)

- Each new or changed command: schema, description and undo covered by tests. Add one example of the command, with the state it runs from, to `examples()` in `crates/commands/tests/it/contract.rs` (the catalog test there proves its description and both schemas; the harness `commands::testing::check` proves the metadata rules and the undo: apply, undo restores the state, redo), and one `check_refusal` case per refusal of the command (the state stays intact). A declared command without an example fails the tests.
- The parity test passes: every command is exposed as an MCP tool, and no MCP tool exists without its command.
- A field a command takes as `null` is nullable in its tool schema (#561): `every_field_a_command_takes_as_null_is_nullable_in_its_schema` sets each top-level field of each command's schema to `null` in its example (nested fields are out of its reach), and when the command still deserialises the schema must validate it. A required `Option` field needs `#[schemars(required, transform = crate::contract::allow_null)]` (schemars drops its `null` otherwise), or a `schema_with` that writes it.
- Each MCP tool's schema carries only the definitions its fields reach (#559): `each_tool_schema_holds_exactly_the_definitions_it_references` and `trimmed_tool_schemas_validate_the_examples_as_the_whole_definitions_did` (`crates/commands/tests/it/contract.rs`, the second through the `jsonschema` validator, draft 2020-12, on every example and its mutations) prove it validates as with every definition. `web/scripts/gen-protocol.mjs` refuses to write a `web/src/lib/generated/schema.json` above 5 MB (`SCHEMA_MAX_BYTES` in `web/scripts/schema-size.mjs`) and names the size of each section; `pnpm gen:check` runs it in CI. The file was 55 MB on 2026-11-03 (every tool carried every definition) and 1.35 MB after the fix, for 136 commands.
- Drive the change from a real agent: connect Claude Code to the helper's MCP server and run the command, then check the result in the page and in the history (author shown, undo works). How (AG-1, #97): run a debug helper on a free port with its own config folder (`FAULK_HELPER_CONFIG_DIR`), `FAULK_HELPER_TEST_NO_TRAY=1`, and `FAULK_HELPER_TEST_SILENT_OUTPUT=1` on a machine without an audio output (a debug build then plays to a silent 48 kHz output, so that a Boost session opens); create the MCP token with `faulk-helper mcp-token` (same `FAULK_HELPER_CONFIG_DIR`); serve the page with `VITE_FAULK_HELPER_PORT=<port>`, start audio, store the helper's `session-token` as the page's `faulk.helperToken` (or pair); since #608 the page serves agents in Web mode too (its control link), so check both modes, and the helper without an output (`FAULK_HELPER_TEST_NO_AUDIO=1`); then run `claude -p "<prompt>" --mcp-config <file> --strict-mcp-config --allowedTools "mcp__faulk__<tool>"` with a config whose server `faulk` runs `faulk-helper mcp --port <port>` with the same `FAULK_HELPER_CONFIG_DIR`. The tool names are the commands' with `_` for `.` (`track_create`).
- The whole agent path in a browser (AG-5, #101): `agent-scenario.spec.ts` builds the debug helper (`cargo build -p helper`, in the spec's `beforeAll`; CI installs `libasound2-dev` first when the plan holds the spec), starts it on the checkout's helper port without an audio output or a tray, with its own config folder and MCP token, pairs the page with its session token and drives it as an MCP client over `faulk-helper mcp` (stdio): `project.new` allowed in the page, three MIDI tracks and an audio track, two scenes of clips, a lane on a Filter's cutoff, a scene launched, then the arrangement played. ### Timing budgets of the e2e specs

`engine-mo2.spec.ts` (the shipped worklet) measures the cost of the engine channel on the render thread of a real AudioWorklet: 2 µs per pumped message and 500 µs for the longest pump (the swap of a table at its limit), budgets of CT-3 and MO-2. `engine-channel.spec.ts` is the CT-3 prototype, kept as the evidence of the chosen way (and of way (a), which was not shipped); it holds ceilings only, in every mode (10 times 2 µs and 500 µs, and 500 µs per message for a burst of way (a), whose own bound is 50 µs). Every number is printed, with the mode (`timing: ceiling…` or `timing: STRICT…`); in strict mode each of the five runs is printed and checked, then the asserted medians.

- **CI and default**: the assertions hold a ceiling ten times the budget (20 µs per message, 5 000 µs for the longest pump). A shared runner is slower and noisier than a workstation (in the prototype spec (way (b), which moves 8 192 slots and a million notes in a pump) the longest pump measured 512 µs in CI run 38705342790 of `develop`, 1 049 µs in the report of #220, and up to 1 201 µs in 20 local runs on a Windows workstation that was also running other work; the shipped worklet (`engine-mo2`) measured 15 µs median and 169 µs at most over 40 such runs, and once 2.40 µs per message against a budget of 2: one preempted quantum is enough), so the ceiling only catches a gross regression (about 65 times the measured per-message cost of the shipped worklet, 280 times its longest pump), not an overrun of the budget: that is the strict run's job. The 500 µs swap of 8 192 slots and a million notes (prototype, way (b)) is held by the ceiling only; the strict run measures the shipped worklet's 2 048-entry swap.
- **Strict, on a reference machine**: `FAULK_E2E_STRICT_TIMING=1` runs the shipped measurement five times and holds the budgets themselves on the **median**. A reference machine is a workstation with nothing else running (no build, no other browser), named with its CPU and OS in the pull request; the strict run is never done in CI. Any value other than `1` or `0` is an error.

  ```bash
  cd web && FAULK_E2E_STRICT_TIMING=1 pnpm exec playwright test engine-mo2 --project=dev
  ```

  PowerShell (the variable stays set in the session, remove it afterwards): `cd web; $env:FAULK_E2E_STRICT_TIMING='1'; pnpm exec playwright test engine-mo2 --project=dev; Remove-Item Env:FAULK_E2E_STRICT_TIMING`.

The clock of these measurements (`engine-mo2.spec.ts`, `engine-channel.spec.ts` and the QA-7 bench `web/tests/bench/engine-swap.bench.ts`, #283) is a Worker spinning on a shared counter, because an AudioWorkletGlobalScope has no `performance`. That loop runs about six times slower during its first 200 to 800 ms, so each harness waits until three windows of 200 ms agree before the load starts; `engine-mo2` and the bench also convert each report at the rate measured over the window it covers (a `rate` message just before `report`) and fail when it differs by more than 25 % from a calibration taken after the load; the printed `clock … ticks/µs (check …)` shows both. Requests to the Worker and the worklet (`fixtures/measure-rpc.js`) have a deadline and reject on an error reply, a Worker error event or the node's `processorerror`, so a stall fails by name (`prepare Worker: no reply to "push" within 15000 ms`) instead of running to the test's timeout. The first pump that applies messages after a reset is printed apart (`first …`): V8 compiles a wasm function the first time it is called, on the audio thread, so that pump is cold (67 to 579 µs on the heavy project's stream, once; up to 1 367 µs in an earlier series) against 26 to 48 µs for the others. Since #355 the worklet runs `fk_warm` (`engine::warm`) in its message handler before any audio: every message of the engine goes once through a private channel (tracks, the devices of the registry, clips, an audio source, an arrangement, automation, the launch grid, the transport with sounding notes, the removals and a second `Reset`), so that V8 compiles those functions there and the first pump that applies messages is warm (the bench: median of five runs 10 µs, against 1 342 µs without the warm-up, see the QA-7 spike). `FAULK_BENCH_FIRST_MAX_US=<µs>` asserts the first pump under that figure (for a quiet machine); `FAULK_BENCH_WARMUP=0` skips the warm-up to measure the cold start again; the bench prints the time the worklet's initialisation takes with it (about 10 ms more, in the message handler, before the node is connected). `engine-mo2` asserts the longest of both because its engine has already applied the setup; the bench prints both and asserts neither unless `FAULK_BENCH_FIRST_MAX_US` is set (it then asserts the first). `FAULK_BENCH_JSFLAGS=--no-wasm-lazy-compilation` (Chromium's `--js-flags`) removes the cold pump too and tells whether a spike is a first call; `FAULK_BENCH_WARM=<n>` sends the first n pushes of the stream before the measured window (the count assertions are then off) to show what a warm-up buys.

Run it before a release and after any change to `crates/engine`, `crates/engine-wasm` or `web/src/lib/engine/worklet.ts`; report the printed numbers and the machine in the pull request.

`timegrid.spec.ts` (AR-3) scrolls and zooms the shared time grid over 200 bars for 360 frames and prints the frame interval (mean, p95, worst, share over 20 ms) and the cost of each canvas draw (mean, p95, worst). Its default ceiling (draw p95 under 12 ms) only catches a gross regression, and the frame interval is asserted in strict mode only (#284); `FAULK_E2E_STRICT_TIMING=1` holds 60 images per second (mean under 17.5 ms, under 5 % of frames over 20 ms, draw p95 under 4 ms) on one sweep, not on a median of five. A headless frame interval is locked to the display's refresh, so the draw cost is the figure that shows the headroom. Run it strict, on a reference machine, after any change to `web/src/lib/components/timegrid/`, and name the machine in the pull request.

`piano-roll.spec.ts` (PN-1) loads 2 000 notes into a clip of 50 bars through the dispatcher's dev hook (`__faulkRun`, so that test runs in the `dev` project only) and prints, with the same ceilings and strict mode as above: the cost of a drawn frame (grid plus notes, read from `data-draw-ms` and `data-body-ms` of the grid) while scrolling and zooming, the same while dragging all the notes zoomed out so that every one is in sight, and the time from calling `clip.notes.update` on all 2 000 notes to the frame that shows the result. Run it strict, on a reference machine, after any change to `web/src/views/piano-roll/` or to `TimeGrid`'s `drawBody`.

`automation.spec.ts` (AM-4) loads a lane of 10 000 points through the same hook, zooms all the way out (so that the lane is drawn as pixel columns) and prints the cost of a drawn frame (grid, clips and lane, `data-draw-ms` plus `data-body-ms`) over 240 frames of zoom and scroll, then the cost of a drawn frame and of handling one pointer move (handler, preview of the lane, effects, up to the next microtask) while all 10 000 points are dragged at once; same ceilings and strict mode as above (draw p95 under 4 ms and a move under 8 ms in strict mode). The spec also proves that the engine plays a lane: the master's level (`data-master-peak`, the engine's own report) falls when the play position reaches a volume point, whereas the knob and the fader that follow a lane show the page's reading of it. Run it strict after any change to `web/src/views/arrangement/automation/`.

Frame-rate checks on the shared runner (`grid.spec.ts` "stays fluid", `mixer.spec.ts` "render cost", `piano-roll.spec.ts`; #284): a wall-clock frame interval follows the runner (vsync, neighbours), not the code, so it is printed everywhere and asserted in strict mode only. The ceiling holds the main-thread time the page spent per frame (`mainThreadMeter` in `web/tests/e2e/support.ts`: the browser's task duration over the window), divided by the time a fixed piece of JavaScript takes on the same machine at that moment (the "reference unit"), as the best of three windows, because noise only adds time. `FAULK_E2E_CPU_THROTTLE=4` slows the page's CPU (CDP) to rehearse a slow runner, but only in the specs that create a `mainThreadMeter`, not across the suite (to rehearse any other spec, put `Emulation.setCPUThrottlingRate` in a temporary `beforeEach`; a rate of 6 already keeps the DAW from starting, 3 is workable; #424); the ceilings sit 2 to 3 times above the worst value seen under that 4x slowdown and below what a 5 to 10 times heavier render costs (checked by injecting one). `mixer.spec.ts` "render cost" (`@full`) is the exception, since #739: under a parallel build its main-thread figure moved from 1.3 to 2.0 reference units (the old ceiling was 1.5), because the reference unit is timed at two instants and not across the window, and a CPU-time ratio to the grid view still overlapped the figures of a mixer that did three times the meter work. It now counts the work: style writes per second in the moving mixer (a MutationObserver inside the frame window; the meters follow the engine's 30 Hz reports, so a busy machine lowers the frame rate and not this figure; 1750 to 1815 clean over 10 runs under a cargo build, 3580 with one meter rendered twice, checked by injecting it; ceiling 2600), plus a wide ceiling (12) on the renderer process's CPU time per frame (`SystemInfo.getProcessInfo`) in the mixer view over the grid view's (2.5 to 5.0 clean, 6.7 under `FAULK_E2E_CPU_THROTTLE=4`), which catches a gross regression only: a doubling that adds no style write passes it. Under that 4x slowdown the writes fall (about 600 per second), so the count loses sensitivity there. `keyboard.spec.ts` reads a drum hit's crest from the page (`startPeakHold`), not from a 30 Hz poll that a short sound can fall between.

Clock check of the render-thread timings (`engine-mo2`, `engine-channel`; #283, #359): the timings are read from a Worker spinning on a shared counter, and on a shared two-vCPU runner that counter's pace flips between about 55 and 110 ticks/µs within a run (CI run 40388605597), which makes the figures of the run wrong by up to as much, and taking the run again does not help there. `withStableClock` (`web/tests/e2e/support.ts`) takes a drifted run again: in strict mode up to 4 attempts, then it fails by name (a reference machine must hold its clock); otherwise 2 attempts, then the last run is kept with a printed note and held to the ceilings only, ten times the budgets, which a 2x error cannot hide a gross regression from. The budgets and ceilings are not touched, and a run whose clock held is checked against them as before, so a real regression (a busy loop in the pump, injected to check) still fails in strict mode.

The e2e build sets `VITE_FAULK_DEV_ROUTES=1`: the `preview` project is the production build plus that flag, and the `dist` folder an e2e run leaves behind has the test surfaces switched on.

**Dev hooks in the specs (#626).** The hooks of the dev server (the keys of the `import.meta.env.DEV` block of `web/src/lib/stores/index.ts`: `__faulkRun`, `__faulkView`, `__faulkHistory`, `__faulkOpen`, ...) do not exist in the `preview` project. The zone level of the CI does not run `preview`, so a spec that used one without skipping only failed in the full suite, on another pull request. A test that uses one calls `await skipWithoutDevHooks(page)` (`web/tests/e2e/support.ts`) before the first use, or skips the same test with `test.skip(... !== 'function' ...)` or `test.skip(info.project.name !== 'dev', ...)`, or branches on it with an `if` whose condition reads a presence probe or the project's name (directly, or through a variable that a later `if` tests); a call to a helper of the file that skips counts where it stands. A bare read of the project's name, or a skip the wrong way round, is not a guard. `pnpm test` fails the test "holds for every spec of tests/e2e" of `web/scripts/e2e-dev-hooks.test.ts` otherwise, naming `file:line`, the test and the hook, with no browser. The guard reads the specs as text, per test body (up to the closing `})` at the test's indentation): a top-level helper that touches a hook makes the tests that name it users, unless the helper branches or skips on the project first; a `test.skip` written at the left margin outside every test body covers its file (one inside a `describe` covers none of it: the guard asks each test for its own). It does not prove that the branch is the right one: an `if` on the project's name or on a presence probe counts wherever it stands before the first use, whichever branch holds the hook call, and a probe whose result is ignored passes. It reads only the keys of that one block (a dev-only surface without a hook, as the import button behind `AUDIO_IMPORT_UI`, is not seen), and a test must open with `test('title', ...)` closed at its own indentation (`test.slow()`, `test.fixme()` and the like are not test starts; a closing `}, { timeout })` is not found). Call `skipWithoutDevHooks(page)` once the app has booted (after `engineUp`): before that the hooks do not exist yet and the dev project would skip too. The `preview` project on the release remains the proof.

## CI (GitHub Actions, `.github/workflows/`)

CI runs where it is useful and nowhere else (#330, founder's decisions of 2026-10-24): the code is tested once, in its pull request, and once more as a whole on the release.

| Event | What runs |
|---|---|
| Pull request against `develop` (a task) | Only what the changed files can affect, chosen by `scripts/ci/select.mjs` (below). |
| Pull request against `main` (the `develop` to `main` release, or a hotfix) | The full suite, once: workspace fmt, clippy and tests, both WASM builds, the prototype crate, the helper on Windows, the web checks with the end-to-end tests of both projects (`dev` and `preview`), the agent scripts. |
| Push to `develop` or `main` | Nothing: the jobs of `rust.yml`, `ci.yml` and `agent-scripts.yml` are skipped (`if: github.event_name == 'pull_request'`). No nightly run either. |
| Tag `helper-v*`, dispatch | `release-helper.yml`, unchanged. |

Required status checks (2026-11-01, repository made public): `develop` and `main` are protected: pull request required (no approval count), required checks `rust` and `web` (`web` is the single verdict job of `ci.yml`, which waits for `select`, `checks` and the three `e2e` shards; never require a shard), branch up to date before merging (strict), no force push, no deletion; the protection does not bind admins (`enforce_admins` off) so a hotfix stays possible. On a pull request each required job always starts and reports (success when its heavy steps are skipped), so a skipped test never blocks a merge; they are skipped on a push, where nothing requires them. While a required check runs, GitHub reports the pull request `BLOCKED`: `.claude/tools/merge-queue.sh` waits on it, then refuses to merge unless `rust` and `web` reported green itself, since admin merges are not bound by the protection (#458).

### The web workflow, in four jobs (#372)

`ci.yml` has `select` (the selection above), `checks` (`gen:check`, format check, typecheck, lint, vitest, build), `e2e` (the Playwright specs, `--shard=n/N` on one to three machines (#377: none when the change touches no browser test), each with its own Chromium, dev server and helper port, a trace artifact kept 7 days on failure) and `web`, which only reports the verdict of the others (failure or cancellation of any of them fails it; a skipped job is fine). `checks` and `e2e` run in parallel, so the time is that of the slower. The common set-up (Rust targets, cache, pnpm, Node, install) is the composite action `.github/actions/web-setup`. Playwright's browsers are cached in `~/.cache/ms-playwright`, keyed on the Playwright version of `web/pnpm-lock.yaml`: a miss runs `playwright install --with-deps chromium`, a hit only `playwright install-deps chromium`. Playwright deals whole spec files out between the shards (one worker per machine, as before), so the targeted selection (`FAULK_E2E_PROJECTS`) and the full release run both shard the same way.

### The end-to-end tests of a pull request against `develop` (#377, tiers since #533)

`select` hands the table of `scripts/ci/e2e-plan.mjs` the `web/` files of the change, `ci.yml`, the `Cargo` files and `modules/`, and the files of each changed crate whose own change reaches a crate the page is built from (`engine-wasm`, `project-wasm`, `protocol`). Each file falls on its first rule; the tier of the change is the highest of its files'. Four tiers:

- **area**: the specs of the touched areas, whole but for their `@full` tests (`playwright test <specs> --grep-invert @full --shard=n/N`; below), the specs whose own file changed with every test, plus the **core tests** of the other specs (a second `playwright test <specs> --grep <pattern>`, on the first machine only and unsharded, so that no shard gets a share of the core with no test in it). The areas are named lists (`AREA` in `e2e-plan.mjs`): views, shell dialogs, libraries with one audience, each i18n feature file (the specs of the views that show its keys), each shared component (the specs of the views that mount it, transitively), and three crates outside their contracts: `crates/engine` (the engine's sound and timing specs, `engine-channel` included since the CT-3 prototype builds the crate) and `crates/project`, `crates/project-wasm` (storage, history, refusals), and `crates/helper` (the `helper` area, the agent scenario included, #668).
- **core**: the core tests alone, on one machine, for a shared file of the page that no area owns: `web/src/lib/stores/`, `lib/app/`, `lib/project/`, `lib/meters/`, `lib/styles/`, the other top-level `lib/*.ts`, the app shell (`views/shell/Shell.svelte` and the shell files no area names), `views/registry.ts`, `routes/app/`, the i18n catalogue and helpers (`app.ts`, `index.ts`, `lang.ts`, `feature.ts`), `web/static/`, `app.d.ts`. They replace the whole suite there. A regression that neither the area nor the core sees is caught at the latest by the release pull request of the day, which runs everything.
- **all**: the whole suite on 3 machines, `@full` tests included, for the contracts (`crates/protocol`, `crates/commands`, the engine sync: `crates/engine/src/msg.rs` and `msg/`, `crates/engine-wasm`, `web/src/lib/engine/` except the helper files and the prototype, `web/src/lib/generated/`), the Playwright and CI configuration (`playwright.config.ts`, `tests/e2e/support.ts` and `fixtures/`, `ci.yml`, `.github/actions/`, `scripts/ci/` except an edit of the table alone, below), the build inputs (`web/package.json`, the lockfile, `pnpm-workspace.yaml`, `vite.config.ts`, `svelte.config.js`, `tsconfig.json`, `vercel.json`, `web/scripts/`, `app.html`, `hooks.server.ts`, the `Cargo` files, `modules/`), any path the table does not know, a rule or core entry that names a spec that no longer exists, a spec list that is empty or unreadable. The release pull request (and `verify.mjs --full`) runs the whole suite, on both projects in CI.
- **none** (no `e2e` job, no machine): docs, notes, unit tests, scripts, the formatter settings, the benchmarks, `crates/test-support` alone. `crates/helper` is not here since #668: the browser tests drive the real helper (the agent scenario, AG-5) or its stand-in, so a change of its files selects the `helper` area (`agent-scenario`, `big-project`, `helper`, `local-access`) and the core tests, never the whole suite (`crates/protocol` stays a contract: all).

**An edit of the table alone** (lead's decision of 2026-11-03): when the only file of `scripts/ci/` that changed is `e2e-plan.mjs` and its change is an edit of the table, the change runs the table's tests (the agent scripts job), the core tests and the specs the edit newly names, not the whole suite. The table is the text between the lines `// e2e-table:begin` and `// e2e-table:end` (the `AREA` and `RULES` declarations). `tableOnlyChange` proves the edit strictly: each marker appears once in both versions, the text outside them is identical, every line added or removed between them is a line comment, a whole one-line `/** */` comment, an area entry (a list of spec names on one line) or a rule on one line whose regular expression has no quantified group and whose verdict is `ALL`, `NONE`, `CORE`, an area, a union of areas or a list of spec names, and, since rules are ordered and the first match wins, no file of the repository (`git ls-files`) gets a weaker selection from the new table than from the old one (both are evaluated: all to less, specs dropped, core to none). A rule with a function, code next to a regular expression or after a comment opener, a rule split over lines, a reordered or inserted rule that shadows another, a change to the core, a change elsewhere in the file, a second file of `scripts/ci/` (its test file included), or a base it cannot read: the whole suite, with the reason in `why`. The specs it newly names are the names, and the specs of the areas, that the added lines carry and the removed lines did not. The CI reads the base from the merge commit's first parent, `verify.mjs` from the merge base. Replayed on the 25 pull requests merged before #540 (their real table files, markers added around the old `RULES`): of the 10 that touched only `e2e-plan.mjs` under `scripts/ci/`, the check accepted 8 and refused 2 that narrowed a file's selection; 4 would have run an area instead of the whole suite (the others also touched a contract or the configuration).

**`@full`: tests left to the whole suite** (lead's decision of 2026-11-03). A test with `@full` in its title runs only when the whole suite runs (the release pull request, a contract, the configuration): the area and core runs pass `--grep-invert @full`, and a spec whose own file changed runs whole, `@full` tests included (a third command, `e2e_specs_changed`). They are the repeated variants and the performance ceilings, 22 tests in 16 specs on 2026-11-03 (`playwright test --project=dev --list --grep @full`; the 19 in 14 written before was stale): the performance prints of `mixer` (32 strips), `grid` (stays fluid), `project-save`, `automation` (10 000 points), `history-cost` and `audio-import` (the import of a one-hour file, in Boost; AU-1): their CI ceilings (the gross-regression net described under "Timing budgets of the e2e specs") now hold on the release run and on a change of their own spec, so a gross slowdown of the grid, the mixer or an automation lane made by another file is caught at the latest by the release of the day, and their strict budgets stay checked by hand on a reference machine; the French run of `all-sound-off`, `keyboard`, `refused-commands`, `arrangement-time` and the "French" tests of `project-store` and `browser-storage` (the French texts are checked by `i18n.test.ts` and by the other French tests); the `transport` and `tracks` runs at `en, 1920 px` and `fr, 1280 px` (`en, 1280 px` and `fr, 1920 px` stay); the `layout-4` top bar at 1920 and 1440 px (1280 px stays). `isolation` and `space-bar` carry none. A spec of `FULL_WHEN` (`e2e-plan.mjs`, outside the table) also runs whole, tags included, when a file it proves changes (#737): `pack-stream`, `pack-longtasks` (the only browser tests that read the streamed `.faulkpack` export back) and `pack-import` (the only one of the streamed import), for any file of `web/src/lib/storage/` except its unit tests, `web/src/views/shell/StorageBanners.svelte` and the two `pack.rs` (`crates/project/src/file/`, `crates/project-wasm/src/`), not for `web/src/lib/project/core.ts` nor `crates/project-wasm/src/lib.rs` (its `pw_pack_*` entry points), shared hubs whose pack path `pack-worker.test.ts` runs through the real module (a broken end of export went unseen by the storage area runs until a whole-suite run); a name in it that is no spec is a stale table (the whole suite), and an edit of it is no table-only edit. The other `@full` tests of the storage area stay to the whole suite (French variants, performance prints). No core test may carry the tag: `e2e-plan.test.mjs` renders the title templates and fails if one does. The area run passes `--pass-with-no-tests`, since a spec whose tests are all tagged (`history-cost`, `project-save`) is then empty. The first machine writes the number of `@full` tests the area run leaves out to the run's summary (`playwright test <specs> --list --grep @full`), and `verify.mjs` prints it in its summary. To tag a test, add ` @full` at the end of its title (a template may add it for some of its variants only).

The **core** (`CORE_TESTS` in `e2e-plan.mjs`) is the app's backbone: one entry per whole spec or per test (a fragment of its title or of its `describe`, found once in the spec source by the unit tests). On 2026-11-03 it is 21 tests in 12 spec files, about 66 s of tests on the release runs of 2026-11-02:

The `--grep` anchors each file name on a space or a slash (`(^|[ /])arrangement\.spec\.ts`), so a spec never matches another whose name ends with it (`grid-to-arrangement`); `playwright test <the 12 files> --list --grep <pattern>` prints these 21 tests and no other (checked on 2026-11-03); run alone with the CI's command on the lead's Windows machine, they passed in 59 s. No CI job runs that `--list` check: redo it after a Playwright upgrade (the lockfile change itself runs the whole suite, which uses no grep) or a change to how `playwright.config.ts` names its projects, since the grep reads Playwright's title format.

- **Why**: the decision carries the tier and one line saying which files chose it (`e2e_tier`, `e2e_why`). `select.mjs` writes `e2e tier: <tier>, <what runs> (<why>)` to the run's step summary, the e2e step echoes it, and `verify.mjs` prints the same line in its summary and in `--dry-run`.
- **One table, one plan**: `verify.mjs` takes the end-to-end plan from the same `select` decision as CI (since #533; before, it recomputed it from the `web/` files), so both run the same tier on the same files. The CI still runs what `verify.mjs` leaves out: the helper on Windows, `pnpm build`, and the `preview` project on the release.
- **Machines**: one per 6 area spec files, at most 3; the core tests run on the first machine in addition. A machine costs about 2.5 minutes of set-up (Chromium, WASM build) against about 15 s per spec on average, but a spec costs between 2 s and 62 s (`transport`, `browser-storage`, `project-store`, `grid`, `mixer` are the heavy ones), so a short list of heavy specs can take several minutes on its single machine.

The cost of one machine in the CI run of #380: 16 to 27 s of set-up, 25 s of Chromium, 77 to 103 s of WASM build, then 230 to 270 s of tests for a third of the suite (710 s in all). A selection of a few specs costs the set-up, their own time (2 s to 62 s each in the release runs) and the core tests (59 s measured alone, on the first machine). A rule that sends a file to the wrong area is a hole in the net: when a bug slips through a targeted run, add the file to the table (or to `ALL`) in the fix.

### How a pull request chooses its tests

Each job starts with `node scripts/ci/select.mjs`, which lists `HEAD^1..HEAD` (the pull request merged into its base) and reads the Rust workspace with `cargo metadata --no-deps`. The rules are in `scripts/ci/select-core.mjs`, tested by `scripts/ci/select-core.test.mjs` (`node --test "scripts/**/*.test.mjs"`). A dry run needs no checkout: `node scripts/ci/select.mjs --event pull_request --base develop --files web/src/a.ts crates/engine/src/lib.rs` prints the decision (`--json` for the detail, `--files-from <file|->` for a list).

| Changed file | Effect |
|---|---|
| `docs/`, `.scratch/`, root `*.md`, `LICENSE`, `.gitignore`, issue and pull request templates, `CODEOWNERS`, `dependabot.yml` and notes under `.github/` (not `.github/actions/`), `release-helper.yml` | Nothing. |
| `crates/<name>/` | `fmt` and `clippy` on the workspace; `cargo test -p` for that crate, every crate that depends on it (normal or build dependency, transitively) and every crate that only dev-depends on one of those, so a change to `test-support` retests its users without rebuilding the page (`--workspace` when that is all of them); the WASM build of `engine-wasm` and of `project-wasm` when one of them depends on the changed code (their parity tests run with the tests); `helper-windows` when `helper` is tested; the prototype crate's fmt and clippy when `engine` changes (it depends on it from outside the workspace). The `web` job runs when `engine-wasm`, `project-wasm` or `protocol` depends on the changed code, i.e. when the page embeds the changed code or generates its types from it: a change to `helper` alone runs it too since #668, for the `helper` area of the end-to-end table. The crate's files then go to the end-to-end table, which gives its tier (above). |
| `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/`, `modules/` | All of Rust, `helper-windows`, the prototype crate and the web job. |
| `web/` | The `web` job (`gen:check`, format check, typecheck, lint, vitest, build) and the `dev` end-to-end project, in the tier the table gives (above); no end-to-end run when every changed file under `web/` is a `*.test.ts` outside `tests/e2e/`, a `.md`, or the formatter and lint settings (`web/.prettierrc.json`, `web/.prettierignore`, `web/eslint.config.js`). `.git-blame-ignore-revs` runs nothing. A change under `web/tests/e2e/` also runs the agent scripts job, where the table's tests check that every spec is placed. `web/src/lib/engine/proto/crate/` also runs the prototype crate's fmt and clippy; `web/vercel.json` and `web/src/lib/i18n/helper.ts` also run `cargo test -p helper` (its updater tests read them); `web/vercel.json` also runs the agent scripts. |
| `scripts/`, `.claude/` | The agent scripts (`node --test`). |
| `ci.yml`, `rust.yml`, `agent-scripts.yml` | The jobs they define, in full (for `ci.yml`: the whole end-to-end suite). |
| `.github/actions/` (the composite action `web-setup` of `ci.yml`) | Everything, as for a file the table does not know. |
| `scripts/ci/e2e-plan.mjs` alone under `scripts/ci/`, its change an edit of the table (`tableOnlyChange`, above) | The agent scripts, the web job and the core tests plus the specs the edit newly names. |
| `scripts/ci/` otherwise (the selection itself, the end-to-end table's logic, the tests), a file this table does not know, a crate directory cargo does not list | Everything, as for a release. |

Fail safe: if the file list or the workspace cannot be read (or is empty), the decision is "run everything"; an unknown path never skips a test. A path that a job reads but the table skips lets a broken change through green: add it to `select-core.mjs` and its test in the change that makes the job read it.

Consequences for the lead and for local work:

- A merge does not rerun anything, so two pull requests that are green apart and red together (#273, #303) are caught only if the second one was tested on the current `develop`: before merging, the lead updates a pull request that is behind (`gh pr update-branch`) and waits for its targeted CI (`issue-tracker.md` > Merge and close). If `develop` and the pull request both changed `web/src/lib/generated/`, `gh pr update-branch` would leave the generated files stale or in conflict (#426): `.claude/tools/merge-queue.sh` refuses to update, and `.claude/tools/regen-generated.sh <pr>` does it (merge in a temporary worktree, `pnpm gen:protocol` into the shared Rust target, commit, push; it can wait on a running build of the same Rust target, and its first real run is checked by the pull request's `gen:check`). Both are tested by `scripts/agent/merge-queue.test.mjs` on throwaway repositories with stub `gh` and `pnpm`; never test them against a real pull request.
- The `preview` end-to-end project and the cross-crate parity of an unrelated crate run only on the release pull request. `FAULK_E2E_PROJECTS=dev` (or `preview`) runs one project with its server only; unset, both. The `dev` server does not build the WASM: run `pnpm build` first, as CI does. For a change that can alter the production build (vite config, `vercel.json` headers, adapter, the landing page), also run `pnpm test:e2e --project=preview` locally before the pull request.
- The helper trial build (`release-helper.yml`) no longer follows a merge to `develop` or `main`: a dependency bump in `Cargo.lock` is built and tested on Linux and Windows (`rust`, `helper-windows`) in its pull request, but packaged on macOS only by the next `helper-v*` tag build (a trial build has no macOS leg either).
- Back-merging `main` into `develop` after a hotfix goes through a pull request, so that it is tested like any other change (nothing runs on a push).
- GitHub requires a branch to be up to date before merging (strict protection, 2026-11-01), which makes the update-branch rule mechanical for anyone but an admin.

`release-helper.yml` (Windows and Linux trial build; the macOS leg runs only with a version, i.e. a `helper-v*` tag or a dispatch with a version) runs on a pull request only for the helper's updater, wiring and manifest, `scripts/helper-release/`, `web/vercel.json` and itself (not `Cargo.lock`: it changes for any dependency), on `helper-v*` tags and on dispatch.

After changing a workflow, lint it: `actionlint` with `shellcheck` available. To see the selection work, read the `Select the tests` step of each job in a pull request: a pull request that changes only `docs/` ends with every `heavy` output `false`, one that touches `crates/helper/` only has `rust_test=-p helper`.

**Disk of the `rust` job (#595).** The Linux runner has a limited disk; the workspace's tests built with full debug info (`debuginfo=2`) filled it (`No space left on device`, `ld` killed by a bus error). The job sets `CARGO_PROFILE_DEV_DEBUG=0` (dev and test profiles, founder's decision: CI is not where we debug; debug assertions and the allocation detector are unchanged), deletes the preinstalled .NET, Android, Haskell, CodeQL and Boost folders before building, and ends with a `Disk report` step (`df -h`, `du -sh target`, in the run summary; a warning under 5 GB free). `helper-windows` prints the report (free space, size of `target/`), without the warning. The run summary holds the measured figures.

## Recording the verification

Once the checks pass, record them for the current state of the code:

```bash
node scripts/agent-qa/record.mjs verified --rust "<...>" --render "<...>" ...
```

Each flag holds what was run and what came out. The flags required depend on the changed files; `record.mjs` refuses a record that lacks one and prints the full command:

| Flag | Required when the change touches | Holds |
|---|---|---|
| `--rust` | `crates/`, `Cargo.toml`, `Cargo.lock`, Rust code under `modules/` | fmt, clippy, test, WASM build |
| `--render` | `crates/engine*`, `modules/` | render tests, allocation detector, native/WASM parity |
| `--commands` | `crates/commands`, `crates/helper` | schema, description, undo, command/MCP parity, run from a real agent |
| `--web`, `--browser`, `--exploration` | `web/`, `site/` | typecheck, lint, tests; the Playwright check; the exploration beyond the script |
| `--scripts` | `scripts/`, `.claude/settings.json`, `.claude/agents/` | `node --test` and the manual try |
| `--latency` | `crates/helper`, `crates/protocol`, `crates/engine-wasm`, a `web/` path containing `worklet` | measured numbers and method, or `not measured: <why>` |

`--note` is optional. The records live outside the working tree, in the checkout's git directory: `.git/faulk-qa/` (`.git/worktrees/<name>/faulk-qa/` for a linked worktree), so `git clean -x`, a glob in the tree or a stray edit never reaches them, and each worktree keeps its own. `verifications.json` and `reviews.json` hold the verifications and the delivery reviews, one entry per state of the code and branch, the last 64 of each (`RECORD_LIMIT`, oldest dropped: a state whose record went is asked for it again), so the branches stacked in one checkout keep their own records (#492); the guard looks up the record of the state it judges among them. `last-run.json` and `review.json` still hold the last verification and the last review alone, for the guard of a branch made before the lists (it reads only those), and are read as one more entry; they can go once no branch older than #492 is worked on. `history.jsonl` holds every record. A list is written whole to a temporary file and renamed, so a reader never sees half of it; an unreadable list counts as empty (the stop then asks for the records again). They are written only by `record.mjs` and the hooks; the guard denies the edit tools and the shell write commands on any path through a `faulk-qa` folder.

### The Stop hook

A `Stop` hook (`scripts/agent-qa/qa-guard.mjs`) refuses to end a turn when the session's own tool calls changed the guarded code of a checkout, unless that checkout's current state has a verification record **and** its task branch has a delivery review record (`judge-dredd.md`). Its message lists the exact commands to run.

- **Guarded code**: `crates/`, `web/`, `modules/`, `site/`, `Cargo.toml`, `Cargo.lock`, `scripts/`, `.claude/settings.json`, `.claude/agents/`, tests included. Files ignored by git (`target/`, `node_modules/`, `test-results/`…) never count.
- **Fingerprint**: a hash of the content of the guarded files that differ from the merge base with `develop` (committed or not, untracked included). Any edit changes it and makes the record stale; committing does not. Without a `develop` reference, all the guarded code counts as changed.
- **Who changed the code** (a session is judged only in the checkouts where it is a *writer*):
  - Edit, Write, MultiEdit, NotebookEdit: the session becomes a writer in the checkout of the file the tool targets, when that file is guarded code. Only that file counts, so another writer's concurrent edit never does.
  - Bash, PowerShell, Agent, Task: the `PreToolUse` hook takes the state of each checkout the session works in (its current directory and the project directory) and the `PostToolUse` hook compares after the call. A call that changed the fingerprint makes the session a writer. Agent and Task calls make the lead a writer for what its subagents change during the call in the lead's own checkouts (a subagent's worktree is not measured by the lead's calls; see Limits for how the agent's own calls are attributed).
  - A checkout first seen at the end of a call (the call moved into another worktree) has no state before the call: it gets its baseline from its state after the call, and the call makes nobody a writer there. Visiting a worktree that carries another agent's work never blocks.
  - A call that moved HEAD without authoring code (reflog: checkout, switch, pull, reset, rebase, a merge of `develop` or `main`; `gh pr checkout` is a checkout) is judged only on the uncommitted changes, which such a move carries over untouched unless the call also edited them; the session's baseline then moves to the new state, and a later block message says so. Merging `develop` into a task branch brings code reviewed in its own pull request. A call that commits (`commit (merge)` after resolving conflicts included), cherry-picks, reverts or merges any other branch is judged on the whole fingerprint: that code was not verified here.
  - A call that never gets its `PostToolUse` (denied by another hook or by the user, interrupted, failed) is dropped at the next stop: it attributes nothing.
  - A session is a writer on the branch it wrote on (or the commit, on a detached head). Once it is a writer on the current branch of a checkout, its calls there are no longer measured.
- **Leaving the branch**: at the stop, each branch the session wrote on is judged where it is, not where HEAD is: with the working tree when HEAD is still on it, with its committed content otherwise. Switching to `develop` after committing leaves the branch to verify, and the message says to switch back. A stash made since the session first wrote in a checkout holds code out of the working tree: the stop is blocked until it is popped (or dropped).
- **Session baseline**: the fingerprint the first time the hooks see the session in a checkout (`SessionStart`, a tool call, or a stop). A writer whose checkout is back to its baseline (it undid its changes) is let through.
- **Checkouts**: the hook judges every checkout the session wrote to, wherever it stops; each has its own records.
- **Deferral**: to stop mid-task only to ask the user a question, run `node scripts/agent-qa/record.mjs deferred --reason "<the question>"`. It lets exactly one stop through for the current state of the code. Once used, another one is accepted only after the user writes again (the `UserPromptSubmit` hook records when), whatever the code does meanwhile. It is kept apart (`deferral.json`) and never erases a verification. Never defer at the end of a task.
- **Failure**: fail open, loudly. If the hook cannot compute a fingerprint (git missing, a repository without a commit) or its input has no session id, it lets the turn end and shows the user a warning. Claude Code also stops honouring a Stop hook after eight blocks in a row without a tool call (hooks reference, https://code.claude.com/docs/en/hooks; not measured here).
- **Guard changes**: when `scripts/agent-qa/`, `scripts/agent-review/`, `.claude/settings.json` or `.claude/agents/` differ from the merge base with `develop`, every stop shows the user a warning: the guard that runs is the modified one.

### Threat model

The guardrails exist to stop an honest agent that skips or forgets a step: ending a task without the checks, without the delivery review, or with records of an older state. They do not stop a deliberately evasive agent: one that hides a write from the hooks on purpose (an interpreter, an encoded command, a variable that expands to a path, a background process, deleting state through a path the guard does not recognise) is out of scope. Those ways around are listed below so that nobody mistakes them for protection.

### Limits

- The record holds what the lead declares: the hook checks that the fields are there, not that the checks ran.
- A change made in the very call that enters a checkout (`cd ../other && sed -i …`), or a shell write to an absolute path in another checkout, is not attributed: the hooks measure only the checkouts of the session's current directory and project directory, and that checkout has no state before the call. The next measured call there, or an edit tool on one of its files, is.
- Symbolic links are not resolved by the shell guard: a link created to point at a record or a brief (`ln -s .git/faulk-qa/review.json alias`) and then written through passes. That is deliberate evasion. `brief.mjs` never follows an untracked link, and `run.mjs` refuses to write through one.
- The records are shared by every session of a checkout: one session's deferral can be consumed by another's stop, and a verification or review recorded by another session for the same state counts. Two `record.mjs` runs at the same moment in one checkout (read, add, rename) can lose one of the two entries: the stop then asks for it again.
- A change made by someone else during one of the session's own Bash, PowerShell, Agent or Task calls (between its two measures) is counted as the session's. Modification times cannot settle it: the change and the call overlap in time.
- Background work is not attributed: a command started with `run_in_background`, `&`, `nohup` or `Start-Process`, or a subagent run in the background, writes after its call has returned. A subagent in its own worktree writes to a checkout the lead's calls do not measure: the lead's later checkout or merge of its branch is a move, not an authoring.
- A tool outside the eight above (an MCP server that writes files) is not measured.
- Subagents share the lead's session id: the hooks of their tool calls run with it, and the hook input carries `agent_id` (documented in the hooks reference, "common input fields"). Since #392 the hooks attribute those calls to the agent, not to the lead:
  - a subagent's writer markers carry its id (`wrote-…-<agent>.json`, kept apart from the lead's), its events never write or move the session's baselines, and each of its hook events (before and after a call) refreshes an `agent-<id>.json` record;
  - the lead's `Stop` leaves a subagent's marker unjudged only while the agent is running **and** the root is a `.claude/worktrees/agent-*` folder of the same repository (same git common directory) **and** the root is not the lead's `cwd` or project directory. Anything else is judged as before: an agent writing in the lead's checkout, an agent that went quiet, a lookalike folder, any edit the lead makes itself (its calls have no `agent_id`, so its marker has none; the fingerprint then covers the whole state of the folder, the agent's work included). A subagent's marker never uses a baseline;
  - "running" means not ended, and either an event less than 20 minutes ago (`AGENT_IDLE_MS`) or a call in progress (a `PreToolUse` without its `PostToolUse`, counted for at most 60 minutes, `AGENT_CALL_MS`). An agent ends when its own stop lets it through, or when the lead's Agent or Task call that was running when the agent fired its first event returns (the hooks note the start of each of the lead's launches); an event fired later runs it again. The second signal can err toward blocking (a background agent or a parallel call caught by it is blocked until its next event; and since the hooks fire only for the eight guarded tools, an agent that only reads or thinks for more than 20 minutes looks quiet) and toward passing: an agent whose run began before the lead's call (a background agent continued in the foreground, if Claude Code reuses its `agent_id`) is not ended by that call. Ending every agent active during any foreground call would bring the false block back with every Judge Dredd call;
  - what remains exempt wrongly, and for how long: a background agent whose own `SubagentStop` did not end it (the hook did not run, or the agent was cut off), or one that ended in a foreground call that began after its run did, stays exempt for up to 20 minutes after its last event, or up to 60 minutes when its last call never got its `PostToolUse` (failed, interrupted, denied elsewhere). A lead that ends its session in that window leaves the agent's unverified work unjudged; the next stop after the window judges it. The lead's `Stop` keeps the snapshot of a running agent's call in progress (it drops the others, as before), so a change made by such a call is attributed to the agent when it returns;
  - the agent's own check: `.claude/settings.json` runs `qa-guard.mjs` on `SubagentStop` (founder's decision of 2026-10-29). Given a `SubagentStop` input (`hook_event_name`, `agent_id`) it judges only that agent's markers, without exemption, and marks the agent ended when it lets it through; a `Stop` that carries an `agent_id` without being a `SubagentStop` stays the main thread's. A subagent's stop answers only for its markers in an agent worktree of the repository: its edits in the lead's checkout are judged by the lead's `Stop`, together with the lead's own work, which the subagent could neither verify nor review. The lead's checkout is the one `CLAUDE_PROJECT_DIR` names. For a worktree-isolated subagent, Claude Code passes the lead's project there: on 2026-10-28 the lead's session held writer markers for agent worktrees, which only happens when the subagent's hooks use the lead's state root (`stateRoot` reads `CLAUDE_PROJECT_DIR` first). Were it ever the agent's worktree, the subagent's hooks would keep their markers under that worktree's own git directory (`.git/worktrees/<name>/faulk-qa`), which neither its own stop (it skips the project's checkout) nor the lead's `Stop` (another state root) reads: its work would go unjudged. A captured `SubagentStop` input (#253) would settle it. The tests feed it the input shape of the hooks reference, not a captured one: a `SubagentStop` without a valid `agent_id` judges nothing, touches no baseline or snapshot and says so in a warning, and the agent's work is then judged by the lead's `Stop` once the agent has ended or gone quiet.
- The guard reads command lines only. It removes quotes and escapes the way bash and PowerShell do (`faulk-q""a`, `faulk-\qa`, ``faulk-q`a``) before matching, but deliberate evasion passes: an interpreter (`node -e`, `python -c`), an encoded command (`powershell -EncodedCommand`), a variable or a substitution that expands to a path, or a file writer it does not know.
- A branch the session wrote on and then deleted cannot be judged: the stop lets it through with a warning to the user (one message per marker, shown at one stop only, identical texts merged). The marker keeps the branch's last known commit (`tip`, refreshed at each stop and after each call of a writer); when the branch is settled in `origin/develop`, the marker is dropped silently. Settled means, cheapest first (#590): that commit is in `origin/develop` (a merge, pushed); or one of the first 100 first-parent commits of `origin/develop` after the branch's base has that commit's tree, or, restricted to the paths the branch changed (200 at most), the patch-id of the branch's whole change (a squash merge, also after develop moved); or, only when both local checks fail, `gh pr list --head <branch> --base develop --state merged` reports a pull request merged after the marker was written (an older one that reused the name does not count) whose head is that commit or, fetched locally, descends from it (commits made after that merge are not settled by it). The squash scan is skipped while neither `origin/develop` nor the commit moved since it last failed (`scannedDevelop`, `scannedTip` in the marker): replayed on the last 20 task merges of `develop` (2026-11-03), it recognized all 20 and none of the same changes with one more file, in 3.5 s at worst (a branch with large generated files). GitHub is asked at most once per stop and once per marker every ten minutes (`prCheckedAt`); `gh` absent, offline or failing counts as not merged (15 s timeout). A local check reads the remote-tracking ref without fetching: a stale `origin/develop` falls through to GitHub. Markers written before `tip` existed, a branch deleted unmerged, and a commit made and deleted in one shell call with no hook in between (the known tip is then older) keep the warning or are settled by an older tip: the guard cannot see inside one call. A branch created at develop's tip, never committed on and deleted with its edits carried elsewhere, also counts as merged (its tip is in develop); the carried edits are judged on the checkout's current branch.
- Changing the guard is trusted only after a human reviews the pull request: the agent that edits `record.mjs` or a hook can also run the edited version. The Stop hook warns the user when the guard differs from `develop`; it cannot do more.
- The hooks run through Git Bash on Windows (`node "$CLAUDE_PROJECT_DIR/..."`). Without Git Bash, Claude Code runs hooks in PowerShell, where `$CLAUDE_PROJECT_DIR` is not expanded: the hooks then fail without blocking anything.
